## 1. 우리가 실제로 구축한 구조 (템플릿의 6단계 체인과의 차이 명시)

| 템플릿이 전제한 단계 | 구현 여부 | 실제 매핑 |
|---|---|---|
| 01. Interpreter (의도 분류) | ❌ 미구현 | `focus_instruction` 자유 텍스트를 시스템 프롬프트에 최우선 반영 지시로 직접 주입 — 별도 분류 단계 없음 |
| 02. Retriever (데이터 수집) | ✅ 구현됨 | `BoardStore.list_posts` + `fetch_backlog_issues`(Jira) + `load_voc_excel`(엑셀), `use_board`/`use_jira`/`use_excel` 각각 독립 토글 |
| 03. Summarizer (요약) | ✅ 구현됨* | `build_prompts()` + 생성 LLM **1회 호출**로 요약 생성 (*별도 모듈 아님, 04 Improver와 동일 호출) |
| 04~06. Evaluator / Critic / Refine (자가 루프) | ❌ 미구현 | 자가평가·비판·교정 반복 루프 없음. 스키마 위반 시 **1회만 재시도**(아래 3장) |
| 07. Improver (개선안 생성) | ✅ 구현됨* | Summarizer와 동일 호출에서 `top_issues`(개선안) 동시 생성 |
| 08. Evaluator/Critic (내부 재점검) | ❌ 미구현 | 내부 재점검 단계 없음 |
| 09. 독립 LLM Judge | ✅ **구현·실증됨** | `run_independent_judge()` — 생성과 실제로 다른 provider로 재검증(아래 2장 실제 사례) |
| 10. 최종 판정 | ✅ 구현됨* | `PASS / FAIL / SKIPPED / ERROR` 4단계(*템플릿은 2단계만 전제 — 검증 불가 상태를 통과로 위장하지 않기 위해 세분화) |

### ★ 실제 구현한 핵심 차별화 요소 — 자기평가 편향 배제 (실증 완료)

`app/main.py::_independent_judge_kwargs()`가 생성에 쓴 provider와 **가능하면 반대 provider**를 독립 검증용으로 선택합니다. 두 provider의 키가 모두 없으면 같은 provider로 폴백하되 `cross_model: false`로 정직하게 노출합니다.

**1차 코드 리뷰에서 발견된 실제 결함**: `_independent_judge_kwargs`가 provider를 anthropic으로 전환하면서도, 생성(openai)용으로 설정된 `llm_model`("gpt-4o-mini")을 그대로 들고 있어 Anthropic API에 존재하지 않는 모델명을 요청 → **404 Not Found**가 발생하고 있었습니다. 수정 후에도 Anthropic의 최신 모델(claude-sonnet-5, 확장 사고 모델)이 `temperature` 파라미터 자체를 거부(`400 temperature is deprecated for this model`)하는 2차 문제가 있어 함께 수정했습니다. 두 결함을 모두 고친 뒤 실제로 Anthropic이 독립 심사관 역할을 정상 수행함을 확인했습니다(아래 2장).

### 시나리오 1 — "상담 대기시간과 불친절 관련 불만사항을 중심으로 정책 개선안을 제시해줘"

| 이슈 주제 | 빈도 | 심각도 | 개선안 |
|---|---|---|---|
| 상담 대기시간 | 6 | high | 실시간 대기시간 안내 시스템 + 인력 추가 배치 |
| 상담원 불친절 | 5 | high | 상담원 교육 강화 |
| 상담센터 운영시간 | 1 | medium | 저녁 시간대 운영 확대 |

**독립 Judge(Anthropic) 판정: `FAIL`** (`relevance: false`, 나머지 3개 기준 true)
> "'상담 대기시간' 이슈에 post-10, post-11, post-15가 포함되었으나 이들은 실제로는 보험금 지급/심사 처리 지연에 관한 내용이지 전화 대기시간과 무관하며, '상담원 불친절' 이슈에도 대기시간 관련 post-6이 잘못 포함되어 example_ids가 주장을 정확히 뒷받침하지 못한다... 잘못된 증거 매핑 때문에 relevance 기준을 충족하지 못해 전체 판정은 FAIL이다."

**이 FAIL 판정 자체가 독립 Judge의 실질적 가치를 증명합니다.** 결정적 검증(`example_ids_valid`)은 "존재하는 id인지"만 확인하므로 통과했지만(id 자체는 실재), Anthropic은 그 id가 가리키는 **원문 내용이 실제로는 다른 주제**라는 것을 의미 수준에서 잡아냈습니다 — ID 존재 여부만 보는 결정적 체크로는 절대 발견할 수 없는 종류의 결함입니다.

### 시나리오 2 — "최근 20건의 VOC만 요약해서 핵심 이슈를 파악해줘"

`item_limit=20` 실행 결과 `raw_source_counts: {board: 25, total_available: 25, total_considered: 20}` — 전체 25건 중 최신 20건만 실제로 분석에 쓰였음을 수치로 증명. top_issues 10개 항목 모두 최근 20건(post-9~post-28) 범위 내 id만 근거로 사용.

**독립 Judge(Anthropic) 판정: `PASS`** (4개 기준 모두 true)
> "각 top_issue의 example_ids는 원본 항목 내용과 실제로 일치한다(post-10~15는 지급지연/처리속도, post-9,26은 불친절, post-28 대기시간...). 지급지연 이슈는 진행상황 안내 부재라는 근본원인을 짚어 개선안을 제시했고, 나머지 항목들도 구체적 대상과 빈도 기반 우선순위를 제시해 실행 가능성과 측정 가능성을 확보하고 있다."

### 시나리오 3 — "보험금 지급지연과 처리속도 관련 불만사항을 분석해서 즉시 개선이 필요한 정책안을 제시해줘"

| 이슈 주제 | 빈도 | 심각도 |
|---|---|---|
| 보험금 지급 지연 | 6 | high |
| 처리 속도 개선 요청 | 5 | high |
| 대기시간 안내 부족 | 4 | medium |
| 상담원 응대 퀄리티 | 4 | medium |

**독립 Judge(Anthropic) 판정: `FAIL`** (`relevance: false`, `root_cause_addressing: false`, `feasibility: false`, `measurability: true`)
> "지시사항은 '보험금 지급지연과 처리속도'에 한정했으나 '상담원 응대 퀄리티' 이슈는 상담원 태도 문제로 범위를 벗어나며... post-27(서류 재요청 반복)처럼 명백한 근본원인이 존재함에도 언급되지 않았고, '인력 증원', '프로세스 최적화' 같은 제안은 구체적 대상·우선순위가 없는 구호성 문구에 가깝다."

**3건 모두 HTTP 200, 실제 OpenAI(생성)+Anthropic(검증) 모델 호출 성공. `cross_model: true` — 실제 교차 모델 검증.**

| 단계 | 내용 | 실제 구현 |
|---|---|---|
| **1단계** | VOC 분석 및 정책 개선안 생성 | `_generate_analysis()` — 게시판/Jira/엑셀 데이터를 정규화해 생성 LLM 1회 호출, summary+top_issues 생성 |
| **2단계** | 내부 품질 진단(결정적 검증) | `validate_analysis_schema()` — LLM 출력 스키마(타입/개수/범위) 검증, 위반 시 1회 재시도. **템플릿이 말하는 "6개 멀티 에이전트"는 아니며, 코드 기반의 단일 결정적 게이트입니다** — 이 차이를 숨기지 않습니다 |
| **3단계** | 독립 LLM Judge 평가 | `run_independent_judge()` — 생성과 다른 provider로 4가지 의미 기준 + `example_ids_valid`(결정적) 채점 |

### 3.1 역할 구분 — 결정적 검증(2단계) vs 독립 Judge(3단계)

템플릿은 Evaluator·Critic이라는 별도 LLM 에이전트를 상정하지만, 실제로는 **코드 기반 결정적 검증**과 **LLM 기반 의미 검증**이라는 두 개의 서로 다른 성격의 게이트로 그 역할을 나눠 구현했습니다.

| 구분 | 무엇을 하는가 | 실행 주체 | 실패 시 |
|---|---|---|---|
| 2단계(Evaluator 역할에 해당) | 출력이 스키마를 지키는가(타입, 개수, 범위) | 코드(`validate_analysis_schema`/`validate_judge_schema`) — LLM 아님 | 1회 재시도 후 안전 실패(502) |
| 3단계(Critic+Judge 역할에 해당) | 내용이 실제로 타당한가(관련성/근본원인/실행가능성/측정가능성) + 근거 id가 실재하는가 | 생성과 다른 LLM + 코드(`example_ids_valid`) | `FAIL`로 표시(결과는 숨기지 않고 그대로 노출) |

이 두 게이트가 성격이 다른 이유: 스키마 위반(예: frequency가 문자열)은 "형식 오류"라 코드로 100% 결정적으로 잡을 수 있지만, "이 개선안이 실제로 타당한가"는 의미 판단이라 결정적 코드로는 불가능합니다 — 그래서 3단계만 LLM에 맡기고, 2단계는 의도적으로 LLM을 쓰지 않았습니다(비용·속도·신뢰성 모두 이 편이 유리).

### 3.3 결함관리 내역 — 분기 인터페이스 오류 · API 호환성 오류

코드 리뷰에서 지적된 항목 중, 실제로 운영 환경에서 재현·수정까지 완료한 2건의 API 연동 결함입니다(사전에 짐작한 원인이 아니라 실제 로그로 근본 원인을 확인).

| 오류 유형 | 증상 | 근본 원인 | 수정 |
|---|---|---|---|
| Provider 분기 인터페이스 오류 | 독립 Judge가 Anthropic으로 전환됐는데도 `404 Not Found` | `_independent_judge_kwargs`가 생성(openai)용 `llm_model`("gpt-4o-mini")을 그대로 물려줘 Anthropic에 존재하지 않는 모델을 요청 | provider가 실제로 바뀌면 오염 가능 필드(`llm_model`/`llm_key_value` 등) 제거 |

## 5. 왜 해당 개선안이 타당한가 — 독립 Judge의 4가지 기준 (+결정적 검증 1가지)

`build_judge_prompts()`가 강제하는 판정 기준입니다. 4개 중 하나라도 false면 `verdict: FAIL`이며, **`example_ids_valid`(결정적 검증)가 false면 LLM이 뭐라 답했든 강제로 FAIL로 덮어씁니다.**

| 기준 | 판단 내용 | 검증 방식 |
|---|---|---|
| `relevance` | 개선안이 원본 불만과 실제로 연계되는가 | LLM 의미 판단(2장 시나리오 1·3에서 실제로 부적합을 잡아냄) |
| `root_cause_addressing` | 표면 증상이 아니라 근본 원인에 대응하는가 | LLM 의미 판단 |
| `feasibility` | 대상/우선순위가 구체적인가(구호성 아님) | LLM 의미 판단 |
| `measurability` | 개선 효과를 검증할 수 있는가 | LLM 의미 판단 |
| `example_ids_valid` | 근거 id가 실제 입력에 존재하는가 | **결정적 코드 검증**(LLM을 신뢰하지 않음) |

필수 항목(summary/top_issues) 누락 시에는 LLM을 부르지도 않고 즉시 FAIL — 품질 미달 산출물에 불필요한 LLM 비용을 쓰지 않는 사전 게이트입니다.

## 6. 과정에서 점검한 기술적 사항

- **모듈 무결성**: 전체 pytest 컬렉션(362개) 성공으로 문법적 완전성 확인.
- **예외 처리**: 빈 VOC 입력, Jira 조회 실패(502), 잘못된 엑셀 경로(400), LLM 미설정(400), 업로드 용량 초과(413), 지원하지 않는 확장자(400), 스키마 위반(재시도 후 502) — 모두 전용 테스트로 확인.
- **Provider 분기 및 오염 방지**: OpenAI/Anthropic/Custom/None 4가지 분기 + 독립 Judge 전환 시 `llm_model`/`llm_key_value` 오염 방지(16개 테스트).
- **테스트 격리**: 전체 pytest 실행이 실제 운영 파일(설정/실행이력/실사용자 데이터셋)을 건드리지 않는지 9개 테스트로 확인(2차 리뷰에서 발견된 P0, 상세는 결함보고서).
- **게시판 권한 체계**: 삭제=관리자 전용, 수정/노출비노출=작성자 또는 관리자, 댓글 열람 권한 우회 차단(11개 테스트).
- **업로드 보안**: 5MB 상한, `.xlsx`만 허용, 경로 조작 방지(파일명 sanitize), 실패 시 파일 삭제.
- **결과 무결성**: 분석 ID 마이크로초+UUID 충돌 방지, `os.replace()` 원자적 저장, 관리자 삭제 기능.
- **프롬프트 인젝션 방어**: 데이터-지시 구분자 + 신뢰 경계 명시(완전한 방어를 보증하지는 않으나 표준 완화 조치를 적용).
- **E2E 통합 흐름**: HTTP 레벨(`TestClient`) + 실제 브라우저(Playwright, 게시판 CRUD/다중삭제/모달/VOC분석/취소버튼) + 실제 LLM 3개 시나리오, 4개 레이어로 검증.

## 7. 성공적인 품질평가라고 판단하는 근거

**근거 1. 요구사항-테스트 상호 추적성** — [`VOC_분석_파이프라인_결함보고서.md`](VOC_분석_파이프라인_결함보고서.md)의 모든 결함/기능에 전용 회귀 테스트가 대응하며 전부 통과.

**근거 2. 계층형 테스트 아키텍처** — 함수 단위(`qa_agent/voc_analysis.py` 55개) → HTTP API(`board_api` 11개 + `voc_analysis_api` 36개) → provider 분기(9개) → Jira 클라이언트(7개) → 테스트 격리(9개) → 실제 브라우저(Playwright) → 실제 LLM 6개 시나리오(1차 3+2차 3), 7개 레이어.

**근거 3. 네거티브 경로 병행 통과** — 정상 동작뿐 아니라 LLM 실패, 필수 항목 누락, 스키마 위반, 업로드 남용, 권한 우회 시도, **그리고 실제 환경에서 발생한 진짜 API 오류(모델 혼용, temperature 거부)**까지 전부 확인.

**근거 4. 생성-평가 행위 분리 + 실증** — "생성 provider ≠ 검증 provider"가 실제 3개 시나리오 모두에서 `cross_model: true`로 확인되었고, 실제 PASS/FAIL 판정과 그 근거까지 확보.

**근거 5. 영구 보존되는 품질 감사 데이터(삭제 정책 포함) + TXT·XML·HTML 3종 증적 + SHA-256 manifest** — 모든 VOC 분석 실행 결과는 `reports/voc_analysis/voc_{timestamp}_{uuid}.json`으로 저장되어 "지난 분석 이력"에서 재조회 가능하며, **관리자가 명시적으로 삭제하기 전까지는 자동 만료되지 않습니다.** `scripts/run_quality_audit.py`가 한 번의 실행으로 **사람이 읽는 로그(TXT), CI 연계용 JUnit(XML), 브라우저용 시각적 리포트(HTML)** 3종과, 세 파일의 SHA-256 해시·생성 시각·git SHA·JUnit tests/TXT passed/`--collect-only` 3중 카운트 일치 여부를 담은 manifest JSON을 동시에 산출합니다. 2차 개정 시점에 실제로 재실행해 358개 테스트 전체에 대한 4개 파일이 정상 생성되고 카운트가 전부 일치함을 확인했습니다(`reports/exports/audit_manifest_20260715_155613.json`, 저장소에는 커밋되지 않는 런타임 산출물). 3차 개정에서 추가된 테스트까지 포함한 최신 총계(362개)는 `docs/테스트_결과.md`와 위 품질 대시보드 API가 실시간으로 반영합니다.

**근거 6. 완전 자동화된 재현** — `pytest -q` 한 줄로 362개 테스트가 매번 동일하게 재현됨을 연속 2회 실행 + 실제 파일 SHA-256/mtime 불변 검증으로 확인(테스트 자체가 실제 운영 데이터를 건드리지 않는다는 것까지 포함해 재현성을 검증).

- ✔ **VOC의 구조화된 품질 데이터화**: 자연어 불만을 소스/빈도/심각도/개선안/근거 id까지 연결된 JSON으로 자동 변환·영구 저장(삭제 정책 포함).
- ✔ **자연어 지시로 관점을 좁힌 분석**: "~중심으로", "최근 N건만" 요청을 `focus_instruction`/`item_limit`로 반영, 게시판 포함 여부(`use_board`)까지 독립 제어(2장 실증).

- ✔ **2차 검증 실패가 1차 결과를 파괴하지 않는 회복력**: 설계 의도가 실제 장애(모델 혼용 발견 이전)에서 검증됐고, 수정 후에는 실제 성공까지 확인.
- ✔ **관리자 전용 삭제/이력 관리로 VOC 증적 보호**: 게시글·댓글·분석이력 모두 삭제는 관리자만, 대량 삭제·이력 삭제 기능까지 갖춤.
- ✔ **결함을 스스로 찾아 고치는 품질 프로세스 실증**: 독립 리뷰로 발견된 P0 7건 + P1 6건을 전부 실제로 수정·재검증한 것 자체가, "검증되지 않은 것을 통과로 표시하지 않는다"는 이 보고서의 원칙이 코드에도 일관되게 적용됐음을 보여줍니다.

## 9. 성공 판정의 합리적 범위와 한계

### ✅ 현재 품질 검증이 안전하게 입증된 범위

- 게시판(일반/FAQ/VOC) CRUD·댓글·권한 체계(다중삭제, 열람권한우회 방지 포함) 27개 테스트 전면 통과
- VOC 분석 생성 파이프라인, `use_board`/`focus_instruction`/`item_limit` 옵션, LLM 출력 스키마 검증
- 독립 Judge 로직(4개 의미 기준 + 1개 결정적 기준) 및 provider 교차 선택(오염 방지 포함)
- **독립 Judge의 실제 크로스모델 PASS/FAIL이 실제 API로 확인됨**(1차 보고서의 한계였던 부분 — 해소)
- 업로드 보안(용량/확장자/경로조작 방지), 결과 ID 충돌 방지, 프롬프트 인젝션 완화 조치
- 2차 검증 실패 시 우아한 성능저하(실제 장애로 실증) + Judge 오류 메시지 정제(`logger.exception`으로 서버 로그에만, 사용자에게는 정제된 메시지)
- **전체 pytest 실행이 실제 운영 데이터를 건드리지 않음**(2차 리뷰 P0-1, 회귀 테스트 9건 + 연속 2회 실행 해시 비교로 실증)
- **quality_gate 판정이 현재 코드로 실제 재현됨**(서버 재시작 후 3개 시나리오 재실행, 1건 APPROVED 실증)

### ⚠️ 추가 검증이 필요한 한계 (정직하게 남기는 범위)

- **테스트 스위트가 일부 실제 문서 파일에 영향을 줌**: `docs/테스트_결과.md`는 `conftest.py::pytest_terminal_summary`가 **모든 pytest 실행마다 항상 최신 결과로 재생성하도록 설계된 프로젝트 전체의 의도된 정책**입니다(이 문서 자체에 "자동 재생성" 안내가 명시돼 있음). VOC 기능이 아니라 프로젝트 전체 테스트 인프라의 사전 결정이라, 이번 리뷰 범위에서 임의로 되돌리지 않았습니다 — 변경하려면 별도의 프로젝트 차원 결정이 필요합니다. 반대로 `.env`의 실제 API 키를 pytest가 사용하지 않는 것(`_no_real_secrets_in_tests` autouse 픽스처)과, 자동화된 pytest 스위트에 라이브 LLM 호출이 전혀 없는 것(모두 모킹)은 이미 충족되어 있음을 확인했습니다.
- 대량 동시 VOC 처리 성능/부하 미검증
- 개인정보(PII) 마스킹 체계 없음(프롬프트 인젝션은 완화했으나 PII 탐지·마스킹은 별도 기능)
- 보험 등 특정 업종 전문 용어 정확도는 합성 테스트 데이터로만 확인(실제 고객 데이터 아님)
- 서버 측 진행 상태 폴링/백그라운드 실행은 구현하지 않음(클라이언트 취소 버튼만 제공 — 취소해도 서버 쪽 LLM 호출 자체는 계속 진행될 수 있음. 실측 소요시간이 수십 초 수준이라 QA 파이프라인과 달리 폴링 아키텍처까지는 도입하지 않은 의도적 범위 결정)
- 6단계 에이전트 분리 구조(템플릿 원안)는 구현하지 않음 — 현재는 "생성 1회 + 독립 검증 1회"의 2단계 구조
- ~~품질 차트가 완전히 동적이지 않음~~ → **3차 개정에서 해소**: `GET /api/voc-analysis/quality-dashboard`가 `docs/테스트_결과.md`와 `reports/voc_analysis/**/*.json` 전체를 매 요청마다 다시 읽어 계산, 프론트는 하드코딩 없이 이 API로 렌더링(데이터 없으면 "검증 데이터 없음" 표시)
- **`reports/run_run_3.json` ~ `run_run_9.json`은 복구 불가능한 상태로 남아 있음**: 2차 리뷰에서 발견된 실제 데이터 오염 3건 중 2건(`reports/settings.json`의 `jira_base_url`, 실사용자 "alice"의 데이터셋 폴더 더미 27개)은 3차 개정에서 실제로 복구했으나, 이 7개 파일만은 실제 파이프라인 실행 결과와 구조가 동일해 진짜/테스트 산출물을 구분할 방법이 없고 백업도 없어 원본을 복원할 수 없습니다. 재발은 이미 방지됐고(격리 완료), 다음 실제 파이프라인 실행부터 정확한 값이 쌓입니다.
- **원본 코드 리뷰가 전제한 "보험사 VOC" 시나리오 데이터가 현재 게시판에 없음**: 세션 중 합성 게시글이 삭제되고 실제 사용자 피드백(플랫폼 자체에 대한 기능 요청) 5건으로 대체됨 — 그 결과 2차 재검증에서 시나리오 1·3은 "관련 근거 없음"으로 정상 REJECTED됐고, 원래 시나리오 주제로는 더 이상 재현할 수 없는 상태(결함이 아니라 데이터 현황)

**[최종 종합 평가 판정: APPROVED — 식별된 결함은 전부 실제로 해소, 잔여 2건은 결함이 아닌 데이터 현황으로 명시]**

게시판 기반 VOC 수집부터 LLM 분석·개선안 생성, 생성 모델과 분리된 독립 모델의 교차검증까지 실제 코드로 구현하고 143개 전용 테스트(전체 스위트 362개)로 검증했습니다. 독립 코드 리뷰 2회에 걸쳐 지적된 P0 11건(7+4)·P1 8건(6+2) **전부** 실제로 수정했습니다.

**2차 리뷰가 지적한 핵심 — "미검증 상태에서 완료를 주장하지 말라"는 원칙을 코드뿐 아니라 이 보고서 자체에도 계속 적용했습니다.** 1차 개정판의 "344건 증적 생성 완료"·"현재 코드로 검증됨"·"최종 APPROVED"가 실제로는 미검증 상태에서 쓰여졌음을 2차 개정에서 확인·수정했고, 그 과정에서 새로 발견한 잔여 항목(품질 차트 완전 동적화, 오염 데이터 복구)까지 이번 3차 개정에서 전부 실제로 처리했습니다:

- **오염 데이터**: `reports/settings.json`의 `jira_base_url`과 실사용자 "alice"의 데이터셋 27개를 직접 검증(더미 여부 확인 후 삭제 / 실제 값으로 정정)해 복구했습니다. `reports/run_run_3~9.json` 7개 파일만은 실제 파이프라인 실행 결과와 구조가 동일해 진짜/테스트 산출물을 구분할 근거가 없고 백업도 없어 **원천적으로 복구 불가능**함을 확인했습니다 — 이는 코드 결함이 아니라 되돌릴 수 없는 데이터 손실이며, 재발은 이미 방지되었습니다.
- **품질 차트**: `GET /api/voc-analysis/quality-dashboard`를 신설해 `docs/테스트_결과.md`와 VOC 분석 전체 실행 이력(`reports/voc_analysis/**/*.json`)을 매 요청마다 다시 읽어 계산하도록 전환했습니다. 프론트는 더 이상 숫자를 하드코딩하지 않으며, 데이터가 없으면 0/성공값으로 위장하지 않고 "검증 데이터 없음"을 표시합니다(전용 테스트 4건으로 검증).
- **원본 시나리오 데이터**: "보험사 VOC" 합성 데이터가 세션 중 삭제되고 실제 사용자 피드백으로 대체된 것은 코드 문제가 아닌 데이터 현황이며, 그 상태에서도 시스템이 "관련 근거 없음"을 정확히 판정(REJECTED)한 것 자체가 결정적 안전장치가 실제로 작동함을 보여주는 증거입니다.
