python -m venv .venv

## 2. 환경변수 설정 (`.env`)

`.env.example`을 복사해 `.env`를 만들고 필요한 값을 채웁니다. `.env`는 `.gitignore`에 등록되어 있어 커밋되지 않습니다.

| 변수 | 필수 여부 | 용도 |
|---|---|---|
| `OPENAI_API_KEY` | 선택 | LLM Judge/근거성 보정/회귀 LLM 판정/루브릭 사용 시 필요. 미설정 시 해당 항목만 `errored` 처리되고 나머지 파이프라인은 정상 진행됩니다. |
| `OPENAI_MODEL` | 선택 | 기본값 `gpt-4o-mini` |
| `ANTHROPIC_API_KEY` | 선택 | `LLM_PROVIDER=anthropic`일 때 필요 |
| `ANTHROPIC_MODEL` | 선택 | 기본값 `claude-sonnet-5` |
| `LLM_PROVIDER` | 선택 | `openai`(기본) / `anthropic` / `custom`(직접 개발한 LLM 연동) / `none`(LLM 관련 평가 전부 비활성화). 4.1절 참고 |
| `LLM_KEY_NAME, LLM_KEY_VALUE, LLM_ENDPOINT` | `LLM_PROVIDER=custom`일 때 필요 | 커스텀 LLM 게이트웨이 인증 헤더 이름/값과 엔드포인트 |
| `SLACK_WEBHOOK_URL, DISCORD_WEBHOOK_URL, TEAMS_WEBHOOK_URL` | 선택 | 실행 완료 알림 |
| `JIRA_BASE_URL, JIRA_EMAIL, JIRA_TOKEN, JIRA_PROJECT` | 선택 | 카테고리별 실패율 초과 시 자동 티켓 생성 |
| `ADMIN_SETUP_CODE` | 선택 | 공개 도메인 배포 시 최초 가입자의 관리자 선점을 막는 코드. 2.2절 참고 |

로컬 실행 시 `app/main.py`가 시작될 때 `python-dotenv`로 `.env`를 자동으로 읽어 `os.environ`에 반영합니다. Docker 실행 시에는 `docker-compose.yml`의 `env_file: .env` 설정이 동일한 역할을 합니다.

> 테스트(`pytest`)는 `conftest.py`의 자동 픽스처가 이 비밀값들을 매 테스트마다 강제로 비웁니다 — 개발자의 `.env`에 실제 키가 있어도 테스트가 실제 네트워크를 호출하지 않도록 하기 위함입니다.

### 2.1 LLM 연동 선택 (`llm_provider`)

`llm_quality`/`rubric`/근거성·회귀의 LLM 보정 판정은 LLM 연동이 필수가 아니라 **선택**입니다. `qa_agent/llm_client.py::OpenAIJudgeClient`가 4가지 모드를 지원합니다.

| provider | 필요한 값 | 동작 |
|---|---|---|
| `openai`(기본) | `OPENAI_API_KEY` | OpenAI Chat Completions API 호출 (`Authorization: Bearer {key}`) |
| `anthropic` | `ANTHROPIC_API_KEY` | Anthropic Messages API 호출 (`x-api-key` 헤더, `{base_url}/messages`). 모델 응답 텍스트를 JSON으로 파싱하며, 마크다운 코드펜스(` ```json `)로 감싸 응답한 경우 자동으로 벗겨냅니다 |
| `custom` | `LLM_KEY_NAME, LLM_KEY_VALUE, LLM_ENDPOINT` | 직접 개발/운영 중인 LLM 게이트웨이 호출. `{LLM_ENDPOINT}/chat/completions`에 `{LLM_KEY_NAME: LLM_KEY_VALUE}` 헤더로 요청하며, **OpenAI 호환 요청/응답 스키마**(`messages, choices[0].message.content`)를 따르는 엔드포인트여야 합니다 |
| `none` | 없음 | LLM 관련 평가를 전부 건너뜀(`errored=True`) — 키가 설정되어 있어도 강제로 비활성화 |

대시보드에서는 "LLM 연동" 드롭다운으로, API 호출 시에는 `/api/run`·`/api/settings` 페이로드의 `llm_provider`/`openai_api_key`/`anthropic_api_key`/`llm_key_name`/`llm_key_value`/`llm_endpoint` 필드로 선택합니다.

### 2.2 회원가입 로그인 (공개 도메인에 올릴 때)

이 플랫폼은 원래 LAN 내부용으로 인증 없이 쓰도록 설계돼 있습니다. 공개 도메인에 올려서
인터넷 어디서든 접속 가능하게 하고 싶다면, 별도 설정 없이 **첫 방문자가 회원가입
(`/signup`)하는 순간부터** 로그인이 자동으로 켜집니다.

- **최초 가입자는 자동으로 관리자로 승인**되어 바로 로그인 상태가 됩니다. 그 이후 가입
  신청자는 전부 "승인 대기" 상태로 시작하며, 관리자가 대시보드의 "사용자 관리" 탭에서
  승인/거부하기 전에는 로그인할 수 없습니다.
- **가입 사유/소개 + 연락처(필수)**: 관리자가 승인 여부를 판단할 때 신청자가 누구인지 알 수
  있도록, 가입 화면에서 본인 소개(신청 사유, 최대 300자)와 연락처(이메일/전화번호 등, 최대
  100자)를 함께 입력받습니다. 둘 다 비어 있으면 가입 자체가 거부됩니다. 관리자는 "사용자
  관리" 탭 표의 "연락처"/"가입 사유·소개" 열에서 승인 전에 바로 확인할 수 있습니다.
- **관리자 선점 방지(`ADMIN_SETUP_CODE`)**: 계정이 하나도 없는 배포 직후 틈을 타 외부인이
  먼저 가입해 관리자를 선점하는 것을 막고 싶다면 `.env`에 `ADMIN_SETUP_CODE`를 채워두세요.
  값을 채워두면 계정이 하나도 없는 동안 가입 화면에 "관리자 설정 코드" 입력란이 나타나고,
  이 값을 정확히 아는 사람만 최초 가입으로 관리자가 될 수 있습니다(틀리면 가입 자체가
  거부됩니다). 두 번째 가입자부터는 어차피 "승인 대기"로 시작하므로 코드가 필요 없습니다.
  비워두면(기본값, LAN 내부용) 기존과 동일하게 코드 없이 최초 가입자가 자동 관리자가 됩니다.
- **관리자 권한 양도**: "사용자 관리" 탭에서 다른 승인된 계정에 관리자 권한을 부여하거나
  회수할 수 있습니다. 단, 마지막 남은 관리자는 스스로도 강등/삭제할 수 없습니다(락아웃 방지).
- **그룹 관리 + 사용 중지/재개**: "사용자 관리" 탭은 계정을 **승인 대기 / 관리자 그룹 / 일반
  사용자 그룹** 3개 섹션으로 나눠 보여줍니다. 각 계정은 삭제하지 않고도 "사용 중지"할 수
  있어 로그인만 즉시 차단하고(이미 로그인해둔 세션도 즉시 강제 로그아웃) 데이터/이력은
  그대로 남으며, 나중에 "사용 재개"로 되돌릴 수 있습니다. 마지막 남은 관리자는 중지할 수
  없습니다(락아웃 방지, 삭제와 동일한 규칙).
- **오류 로그(관리자 전용)**: QA 파이프라인/VOC 분석/교차검증 매트릭스 실행이 실패하면
  화면에는 "LLM 설정과 서버 로그를 확인하세요" 같은 안내 문구만 표시됩니다(내부 경로·설정값
  노출 방지). 실제 원인(예외 메시지, 스택트레이스)은 "오류 로그" 탭에서 확인할 수 있으며,
  최근 200건까지 서버 메모리에 보관됩니다(서버 재시작 시 초기화, 별도 파일 저장 없음).
- **접근 허용 IP(관리자 전용)**: Grafana(3000)/Prometheus(9090) 포트를 인터넷에 직접 열지
  않고도 이용할 수 있도록, "접근 허용 IP" 탭에서 IP 주소(예: `203.0.113.5`) 또는 CIDR
  대역(예: `203.0.113.0/24`)을 등록·수정·삭제할 수 있습니다. 여기 등록된 IP/대역에서
  접속할 때만 `/grafana-proxy`, `/prometheus-proxy` 경로(이 앱의 로그인을 거친 뒤 내부적으로
  Grafana/Prometheus에 연결해주는 통로)를 통과시키고, 그 외에는 403으로 차단합니다. 계정이
  하나도 없는 LAN 모드에서는 이 목록과 무관하게 항상 허용되며(다른 관리자 기능과 동일한
  정책), 계정이 있는 배포(공개 배포로 간주)에서 목록이 비어 있으면 기본값은 **거부**입니다 -
  AWS 등에 배포한 뒤 가장 먼저 자신의 접속 IP를 등록해야 이 기능을 쓸 수 있습니다.
  등록할 IP를 직접 알아내야 하는 번거로움을 없애기 위해, **화면 우측 상단 로그아웃 버튼
  왼쪽에 "내부 IP"와 "공인 IP"를 함께 표시**합니다(모든 탭 공통, `/monitoring-addon`과 차트
  확대보기 페이지에도 동일하게 표시). **내부 IP**는 서버가 IP 허용 여부를 판단할 때 쓰는 것과
  완전히 같은 값(리버스 프록시 뒤에서는 `X-Forwarded-For` 헤더 기준)이라, 같은 LAN/사무실에서
  접속 중이면 이 값을 그대로 등록하면 됩니다. **공인 IP**는 이 서버가 속한 네트워크가 인터넷에
  나갈 때 실제로 쓰는 IP(외부 조회 서비스로 확인, 5분 캐시)로, 나중에 AWS 등에 공개
  배포했을 때 등록해야 할 값을 미리 참고할 수 있게 함께 보여주는 것입니다(조회 실패 시
  "확인 불가"로 표시).
- **사용자별 데이터 분리**: 로그인한 계정마다 데이터셋/테스트 케이스/실행 이력(결함보고서
  포함)이 서로 분리되어 보입니다 — 다른 계정이 올린 데이터셋이나 실행 결과는 보이지
  않습니다. 단, **모니터링(k6/외부 Uptime/서버 지표)은 계정 구분 없이 전체가 공유**합니다.
  **설정(OpenAI/Jira/웹훅 키 등)**도 전체가 공유하는 전역 값이지만, API 키 등 민감정보를
  포함하므로 **관리자만 조회/변경**할 수 있습니다(일반 승인 계정에는 설정 탭의 "연결 설정"
  카드 자체가 보이지 않습니다).
- **로그인 시도 제한**: 같은 접속(IP)에서 5회 연속 로그인에 실패하면 5분간 그 접속의
  로그인이 잠깁니다(무차별 대입 공격 방지). 계정이 하나도 없는 LAN 모드에서는 로그인
  자체가 없으므로 적용되지 않습니다.
- 로그인 안 한 상태로 `/`나 `/api/*`에 접속하면 `/login` 화면으로 이동(API는 401)됩니다.
  로그인 성공 시 브라우저에 세션 쿠키가 저장되어 이후 접속은 자동으로 통과됩니다.
- 로그아웃은 대시보드 우측 상단의 "로그아웃 (아이디)" 버튼(계정이 하나라도 있을 때만 보임)으로 합니다.
- 데이터셋/테스트 케이스 삭제는 업로드한 본인, 또는 관리자만 할 수 있습니다.
- 세션은 서버 메모리에만 저장되므로 **서버를 재시작(예: `docker compose up -d --build`)하면
  로그인 상태가 전부 풀리고 다시 로그인해야 합니다** — 별도 세션 DB 없이 단순하게 유지하기
  위한 의도적인 설계입니다. 계정 자체(아이디/비밀번호/역할)는 `data/users.db`(SQLite)에
  영구 저장되므로 재시작해도 유지됩니다.
- `/health`(헬스체크)와 `/metrics-addon`(Prometheus 스크레이핑)은 로그인 없이도 항상 열려
  있습니다 — 둘 다 자동화된 도구가 쿠키 로그인을 할 수 없기 때문입니다.
- **비상 상황**(관리자 계정이 전부 없어지는 등 승인해줄 사람이 없을 때)에는 서버에서
  `python scripts/create_admin.py <아이디>`를 실행해 승인된 관리자 계정을 바로 만들 수
  있습니다.
- **비밀번호 최소 길이(`PASSWORD_MIN_LENGTH`)**: 신규 가입과 `scripts/create_admin.py`로
  만드는 관리자 계정에만 적용되는 최소 길이입니다(**이미 가입된 사용자의 로그인에는 전혀
  영향이 없습니다** - 길이 검사는 가입/생성 시점에만 이뤄집니다). 값을 설정하지 않으면
  기존과 동일하게 4자이며, 운영 배포(`docker-compose.prod.yml`)는 이 값을 12로 강제합니다.
  가입 화면의 안내 문구와 오류 메시지는 항상 이 값을 그대로 보여줍니다(서버/클라이언트
  불일치 없음).

### 2.3 운영(AWS) 배포 시 보안 강화 설정

로컬/LAN 개발 환경의 기존 동작(평문 HTTP, 인라인 스크립트 자유 사용)을 절대 깨지 않기
위해, 아래 설정은 전부 **기본값이 꺼짐(false)**이고 운영 전용 오버라이드 파일
`docker-compose.prod.yml`을 명시적으로 함께 지정해야만 켜집니다.

```bash
export GIT_SHA=$(git rev-parse HEAD)
docker compose -f docker-compose.yml -f docker-compose.prod.yml build --build-arg GIT_SHA=$GIT_SHA qa-platform
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
```

| 변수 | 기본값 | 운영값(`docker-compose.prod.yml`) | 용도 |
|---|---|---|---|
| `COOKIE_SECURE` | `false` | `true` | 세션 쿠키에 `Secure` 속성을 강제 - HTTPS 연결에서만 브라우저가 쿠키를 다시 실어 보냄. 평문 HTTP인 로컬 개발에서 켜면 로그인이 깨지므로 기본값은 반드시 꺼짐 |
| `TRUST_PROXY_HEADERS` | `false` | `true` | `X-Forwarded-Proto` 헤더를 신뢰해 HTTPS 여부를 판단(Nginx/ALB처럼 실제로 신뢰할 수 있는 리버스 프록시가 앞에 있을 때만 켤 것 - 그렇지 않으면 누구나 헤더를 위조해 HTTPS인 척할 수 있음) |
| `SECURITY_HEADERS_ENABLED` | `false` | `true` | 응답에 `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `Content-Security-Policy`, (HTTPS 요청 시)`Strict-Transport-Security` 헤더를 추가. CSP는 기존 인라인 `<script>`/`style="..."` 사용을 깨지 않도록 `script-src`/`style-src`에 `'unsafe-inline'`을 포함(신규 인라인 스크립트 인프라 없이 기존 코드를 그대로 유지하기 위한 실용적 타협) |
| `PASSWORD_MIN_LENGTH` | `4` | `12` | 위 2.2절 참고 |
| `SESSION_TTL_SECONDS` | `2592000`(30일) | `604800`(7일) | 로그인 세션의 서버 측 만료 시간(초). 세션 자체는 `data/sessions.db`(SQLite)에 영속화되어 재배포에도 로그인이 유지되지만, 그만큼 탈취된 쿠키의 유효기간도 함께 늘어나므로 운영에서는 더 짧게 강제 |

또한 `docker-compose.prod.yml`은 다음도 함께 강제합니다.

- Grafana 익명(Viewer) 접속 끄기(`GF_AUTH_ANONYMOUS_ENABLED=false`) - 로컬 개발용 기본값(익명 허용)과 다름
- `GRAFANA_ADMIN_PASSWORD` 환경변수(또는 AWS Secrets Manager)가 없으면 `docker compose config/up` 자체를 실패시켜 운영에서 `admin/admin` 기본 비밀번호가 그대로 쓰이는 사고를 원천 차단

`docker-compose.yml`의 Grafana(3000)/Prometheus(9090) 포트도 `127.0.0.1:PORT:PORT`로만
바인딩되어 있어(내부 Docker 네트워크의 서비스명 접속에는 영향 없음), 외부 인터넷에서
직접 접근할 수 없습니다 - 반드시 2.2절의 "접근 허용 IP"로 등록된 IP만 `/grafana-proxy`,
`/prometheus-proxy`를 통해 접근합니다.

### 2.4 운영 안정성 강화 (세션 영속화 / 백업 / 리소스 관리)

로컬 개발 환경(`docker compose up -d qa-platform`만 띄우는 경우 등)에서는 아래 항목이
전혀 새 설정 없이도 기존과 동일하게 동작합니다 - 전부 `docker-compose.yml` 기본값에
포함돼 있습니다.

- **로그인 세션 영속화**: 이전에는 로그인 세션이 서버 메모리에만 저장돼 컨테이너를
  재시작(`docker compose up -d --build` 등 재배포 포함)할 때마다 전체 로그인이 풀렸습니다.
  이제는 `data/sessions.db`(SQLite)에 저장되어 재배포해도 로그인이 유지됩니다. 서버 측
  만료(`SESSION_TTL_SECONDS`, 위 표 참고)가 지나면 자동으로 무효화됩니다.
- **Prometheus/Grafana 데이터 영속화**: TSDB(지표 이력)와 Grafana 내부 설정을 각각
  `prometheus-data`/`grafana-data` 네임드 볼륨에 저장 - 컨테이너를 재생성해도 지표 이력과
  Grafana 관리자 비밀번호 등 내부 설정이 사라지지 않습니다.
- **컨테이너 리소스 제한**: qa-platform(메모리 1GB/CPU 1.5개), Prometheus(512MB/1개),
  Grafana(512MB/1개)로 각각 상한을 둬, 한 서비스의 메모리 누수가 단일 EC2 인스턴스
  전체를 먹통으로 만드는 것을 방지합니다. 인스턴스 사양에 따라 `docker-compose.yml`에서
  직접 조정하세요.
- **로그 로테이션**: 3개 서비스 모두 로그 파일을 10MB × 3개(최대 30MB)로 제한 - 로그
  수집 파이프라인이 없는 단일 인스턴스에서 로그가 디스크를 무한정 채워 서비스가 멈추는
  사고를 방지합니다.
- **Prometheus/Grafana 헬스체크**: `docker ps`/`docker compose ps`에서 두 서비스의
  상태(healthy/unhealthy)를 바로 확인할 수 있습니다(qa-platform은 기존부터 `/health`
  기반 헬스체크가 있었음).
- **Grafana Live(실시간 스트리밍) 비활성화**: 앱의 리버스 프록시(`/grafana-proxy`)는
  일반 HTTP만 중계하고 WebSocket 업그레이드를 지원하지 않습니다. Grafana Live가 켜져
  있으면 실시간 갱신 기능만 계속 실패하므로, `GF_LIVE_MAX_CONNECTIONS=0`으로 꺼서 해당
  기능이 자동으로 폴링 방식으로 동작하게 했습니다(다른 차트/대시보드 기능에는 영향 없음).
- **데이터 백업**: `python scripts/backup_data.py`를 실행하면 `data/`의 모든 SQLite
  파일(계정/세션/게시판/IP허용목록/모니터링 애드온)을 SQLite 온라인 백업 API로 안전하게
  복제하고, `reports/`를 통째로 `.tar.gz`로 압축해 `backups/{시각}/`에 저장합니다(호스트에
  바인드 마운트되어 컨테이너 재생성과 무관하게 남음). 운영에서는 EC2의 crontab에 다음처럼
  등록해 매일 자동 실행하세요.

  ```bash
  0 3 * * * cd /path/to/project && docker compose -f docker-compose.yml -f docker-compose.prod.yml exec -T qa-platform python scripts/backup_data.py >> backups/backup.log 2>&1
  ```

  기본적으로 최근 7개 스냅샷만 보관하고 그보다 오래된 것은 자동 삭제합니다
  (`BACKUP_RETENTION_COUNT` 환경변수로 조정, `0`이면 삭제 안 함). **진짜 재해 복구까지
  대비하려면 `backups/` 디렉터리를 주기적으로 S3 등 외부 저장소로 옮기는 것을 권장합니다**
  (이 스크립트 자체는 인스턴스 로컬 디스크에만 저장하므로, 인스턴스 자체가 완전히
  사라지는 사고에는 별도 오프사이트 백업이 필요합니다).

### 2.5 버전 고정 / 배포 검증 / IaC (P2)

- **이미지 버전 고정**: `docker-compose.yml`의 Prometheus/Grafana 이미지를 `:latest`
  대신 실제 검증한 버전(`prom/prometheus:v3.13.0`, `grafana/grafana:13.1.0`)으로 고정했고,
  `Dockerfile`의 파이썬 베이스 이미지도 `python:3.12-slim` → `python:3.12.13-slim`으로
  고정했습니다. 오늘 배포한 것과 나중에 다시 빌드한 것이 서로 다른 버전을 받는 것을
  방지합니다 - 버전을 올리고 싶으면 이 태그들을 의도적으로 바꾸고 변경 이력에 남기세요.
- **배포 검증 스크립트**: 재배포 직후 `python scripts/verify_deployment.py --expected-git-sha
  $(git rev-parse HEAD)`를 실행하면 (1) `/health`가 실제로 응답하는지, (2) 응답의 `git_sha`가
  지금 배포하려는 커밋과 일치하는지(빌드를 깜빡하고 이전 이미지로 재시작한 경우를 잡아냄),
  (3, best-effort) `docker compose ps`의 Docker 헬스체크 상태까지 확인합니다. 실패하면
  0이 아닌 종료 코드를 반환하므로 배포 스크립트/CI에서 그대로 성공·실패 판단에 쓸 수 있습니다.
- **CloudFormation (IaC)**: `infra/cloudformation/ec2-alb-stack.yaml`이 `AWS_배포_운영_매뉴얼.md`에
  문서화된 아키텍처(VPC 2개 AZ + ALB/ACM/Route 53 + 프라이빗 서브넷 EC2 + ECR + Secrets
  Manager + SSM 전용 접속, SSH 없음)를 코드로 그대로 재현합니다. 네트워크/컴퓨트/보안
  경계까지만 자동화하고, 실제 이미지 배포·시크릿 값 입력은 매뉴얼의 수동 절차를 그대로
  따릅니다(자세한 사용법은 `infra/cloudformation/README.md` 참고).

```bash
docker compose up -d --build
```

(모니터링 애드온 포함 전체 스택). 앱 이미지에는 k6 실행 파일도 포함되어 있어 "웹에서 직접

`docker compose up -d qa-platform`을 쓰세요.

`reports/` 디렉터리는 호스트와 바인드 마운트되어 컨테이너를 재시작해도 데이터셋/문서/k6 결과가
유지되고 호스트에서 직접 파일을 볼 수 있습니다. 반면 `data/`(모니터링 애드온 SQLite)는 도커
네임드 볼륨(`qa-platform-data`)에 저장됩니다 - SQLite의 WAL 모드가 Windows 호스트 바인드
마운트에서는 파일 잠금 문제(`disk I/O error`)를 일으키기 때문에, 호스트에서 직접 보이지 않는
대신 도커가 관리하는 볼륨을 씁니다(컨테이너 재시작에도 유지됨).

종료: `docker compose down` / 로그: `docker compose logs -f qa-platform` / 코드 수정 후
재반영: `docker compose up -d --build`

자세한 내용(Feature Flag, 롤백 절차 등)은 11장 "모니터링 애드온" 참고.

## 4.1 윈도우 데스크톱 앱 (브라우저 없이 실행)

서버(위 3장/4장 방식 중 아무거나)는 그대로 두고, 브라우저 탭 대신 **네이티브 윈도우 창**으로
같은 화면을 띄우고 싶다면 `desktop_app/launcher.py`를 실행하거나, 미리 빌드된
`desktop_app/dist/AI_Agent_품질관리.exe`를 더블클릭하면 됩니다.

- 기존 웹 시스템(`app/`, Docker 설정, 화면/API)은 **한 글자도 수정하지 않았습니다** — 이미
  떠있는 서버에 [pywebview](https://pywebview.flowrl.com/)로 접속만 하는 얇은 창일 뿐입니다.
- 브라우저로 접속하든 이 데스크톱 앱으로 접속하든 **같은 서버, 같은 데이터**를 보므로
  두 방식을 동시에 열어놔도 데이터가 항상 동일하게 연동됩니다.
- 서버가 아직 안 떠 있으면 "서버에 연결하는 중입니다..." 대기 화면이 뜨고, 자동으로
  15초간 재시도합니다.

### 다른 PC에서 실행하기 (서버는 다른 컴퓨터에 떠있는 경우)

`AI_Agent_품질관리.exe`는 Python 설치 없이 **다른 윈도우 PC에 파일 하나만 복사**해서
그대로 실행할 수 있습니다. 이때 접속할 서버 주소는 3가지 방법 중 하나로 정할 수 있습니다
(우선순위 순):

1. **환경변수** `QA_PLATFORM_URL` (예: `http://192.168.0.42:8000`) — 가장 우선
2. **연결 화면의 주소 입력창**: 다른 PC에서 처음 실행하면(로컬에 서버가 없으므로) 자동
   연결이 안 되고 연결 화면이 뜨는데, 이때 주소 입력창에 기본값(`http://127.0.0.1:8000`)이
   미리 채워진 채로 자동 선택되어 있으므로 **곧바로 서버 PC의 IP를 타이핑해서 덮어쓰면**
   됩니다(`http://<서버 PC의 IP>:8000`, IP 확인법은
   [팀원용_접속가이드.md](팀원용_접속가이드.md) 참고). 입력 후 "연결" 버튼을 누르면 되고,
   한 번 성공하면 exe 파일 옆에 `server_config.txt`로 저장되어
   **다음 실행부터는 자동으로 그 주소로 접속**합니다.
3. 위 둘 다 없으면 기본값 `http://127.0.0.1:8000`(같은 PC에 서버가 떠있다고 가정) — 다른
   PC에서는 이 기본값으로 자동 연결되지 않는 것이 정상이며, 2번처럼 주소를 입력해야 합니다.

즉, 서버를 띄운 PC에서 쓸 때는 그냥 더블클릭하면 되고, 다른 PC에서 그 서버에 접속해서
쓰고 싶을 때만 최초 1회 주소를 입력해주면 됩니다. 주소를 잘못 입력했거나 서버를 옮긴 경우
연결 화면에서 다시 입력하면 `server_config.txt`가 새 값으로 갱신됩니다.

**필수 전제조건 (다른 PC에서 실행 시 확인)**: 이 exe는 화면을 그리는 데
[Microsoft Edge WebView2 Runtime](https://developer.microsoft.com/microsoft-edge/webview2/)을
사용합니다. 최신 Windows 10/11에는 대부분 기본 설치되어 있지만, 오래되었거나 사내
이미지로 최소 구성된 PC에는 없을 수 있습니다. 없는 상태로 실행하면 (조용히 꺼지는 대신)
설치 안내 메시지 창이 뜨니, 뜨는 링크에서 설치한 뒤 다시 실행하면 됩니다. 그 밖에 실행
직후 문제가 생겨도(예: 쓰기 권한 없는 폴더에서 실행) 원인이 담긴 메시지 창이 뜨도록
되어 있어 "더블클릭해도 아무 반응 없음" 상태로 남지 않습니다.

**직접 실행(파이썬 설치된 경우):**

```bash
pip install pywebview
python desktop_app/launcher.py
```

**exe 다시 빌드하기(코드를 수정한 경우):**

```bash
pip install pyinstaller
pyinstaller --onefile --windowed --name "AI_Agent_품질관리" ^
  --distpath desktop_app/dist --workpath desktop_app/build --specpath desktop_app ^
  desktop_app/launcher.py
```

빌드된 `desktop_app/dist/AI_Agent_품질관리.exe`는 Python 설치 없이 다른 윈도우 PC에도
그대로 복사해서 배포할 수 있습니다(단, 그 PC에서도 서버(Docker 등)에 접속 가능해야 함 —
같은 PC거나, `QA_PLATFORM_URL`을 사내망 서버 주소로 지정한 경우).

## 5. 데이터셋 작성법

`/api/dataset/template`에서 예시 2행이 포함된 Excel 양식을 내려받거나, 아래처럼 JSON으로 직접 작성합니다.

```json
[
  {
    "id": "TC-001",
    "category": "COM",
    "question": "How do I reset my password?",
    "golden_answer": "Use the password reset link",
    "relevant_doc_ids": ["DOC-1"],
    "required_keywords": ["reset", "password"],
    "existing_answer": "Use the password reset link",
    "existing_contexts": ["Use the password reset link on the account settings page."],
    "existing_doc_ids": ["DOC-1"]
  }
]
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `id, category, question, golden_answer` | ✅ | 누락 시 업로드가 즉시 400 에러로 거부됨 |
| `relevant_doc_ids` | 선택 | 없으면 검색품질(`retrieval`) 평가가 자동 생략됨 |
| `required_keywords` | 선택 | `dual_compare` 진단에서 키워드 누락 여부 확인용 |
| `test_type` | 선택 | 예: `functional, regression`. 지정하면 결함보고서.md의 "테스트 유형별 현황"에서 이 값 기준으로 통과/실패가 집계됨(없으면 "미분류") |
| `existing_answer/existing_contexts/existing_doc_ids` | `dataset_only/dual_compare` 사용 시 필요 | 커넥터 모드가 `dataset_only`일 때 이 값을 그대로 재사용 |

카테고리 코드 예시: `COM`(공통), `ACC`(정확성), `REG`(정책), `MTD`(절차), `RPT`(서류), `NFR`(비기능/안전성). 자유 문자열이라 새 값도 바로 사용 가능합니다.

## 6. 웹 대시보드 사용법

대시보드는 **설정 / 실행 / 대시보드 / 모니터링 / 게시판 / VOC 분석 / VOC 분석 결과** 탭으로 구성되며, 관리자 계정에는 **사용자 관리 / 오류 로그 / 접근 허용 IP** 탭이 추가로 보입니다. **모니터링 애드온**(k6/Prometheus/Grafana)은 이 탭들과 별개로 완전히 독립된 페이지(`/monitoring-addon`)로 제공됩니다.

### 설정 탭
1. **커넥터 모드** 선택: `dataset_only`(저장된 답변 재사용) / `mock`(키워드 매칭 임시 답변) / `api`(실제 챗봇 엔드포인트 호출, 엔드포인트 입력 필요)
2. **카테고리 필터**(선택), **LLM 연동**(선택 — `OpenAI`/`Anthropic (Claude)`/`기타(직접 개발한 LLM 연동)`/`사용 안 함` 중 선택. `기타` 선택 시 KEY 이름/KEY 값/엔드포인트 입력란이 나타남. 2.1절 참고)
3. **알림 웹훅/Jira 정보** 입력 후 "설정 저장"으로 저장 가능 (비밀번호 입력란은 "보기" 버튼으로 값을 확인할 수 있음)
4. **데이터셋(정답 기준값) 업로드** - category/golden_answer 등 채점 기준을 담은 파일. 미리보기/현재 파일 다운로드 버튼 제공. 그리고 **문서** 카드에서 문서들을 항상 최신 상태로 조회

> **데이터셋(정답)과 테스트 케이스(발화문)는 서로 다른 개념/파일입니다**: 데이터셋은 "정답이
> 무엇인지"(category, golden_answer, required_keywords 등)를 담고, 테스트 케이스는 실행 탭에서
> 별도로 올리는 "무엇을 물어볼지"(id, question)만 담은 훨씬 가벼운 파일입니다. 테스트 케이스를
> 올리지 않으면 데이터셋 자체에 적힌 question이 그대로 쓰이므로(하위호환), 기존처럼 단일 파일만
> 써도 문제없습니다.

### 실행 탭

1. **테스트 케이스(발화문)**: 데이터셋과 별도로 id+question만 담은 파일을 업로드(선택 사항) - id가 일치하는 데이터셋 케이스의 질문만 이 발화문으로 바뀌어 실행되고, id가 안 맞는 데이터셋 케이스는 이번 실행에서 제외됩니다. 미리보기/다운로드/초기화/업로드 이력 모두 데이터셋과 동일하게 제공됩니다.
2. **데이터셋 사용 안 함** 체크박스: 켜면 정답 비교 없이 테스트 케이스의 발화문만으로 품질 테스트를 진행합니다(LLM 판정이 "정답과 일치하는가" 대신 "질문에 대한 응답으로서 타당한가"를 절대평가). 데이터셋 없이 새로운 챗봇을 처음 살펴볼 때 유용합니다.
3. **테스트 기법** 체크박스에서 실행할 기법 선택 (`rag`/`llm_quality`/`rubric`/`regression`/`functional`/`dual_compare`, 최소 1개 필수)
4. "QA 파이프라인 실행" 클릭 → 활성 데이터셋(+테스트 케이스)을 대상으로 실행되며, 진행률 바 아래에 **단계별 진행사항 체크리스트**(데이터 준비 → 평가 실행 → 리포트 저장 → Jira 티켓 생성 → (웹훅을 설정한 경우만) 알림 발송)가 실시간으로 갱신됩니다 - 지금 어느 단계가 진행 중인지(🔄), 끝난 단계(✅), 아직 시작 안 한 단계(⏳)를 한눈에 볼 수 있고, 실패하면 실패한 단계에 ❌가 표시됩니다. 완료되면 결과/Mismatch 섹션이 갱신됨
5. "CSV 다운로드"/"마크다운 다운로드"로 최신 리포트 다운로드

### 대시보드 탭
개요 지표, 5종 차트(시계열/막대/산점도/버블/방사형), Jira 티켓, 실행 이력을 확인합니다.

### 게시판 탭

일반(잡담) / FAQ / VOC(불만 및 요구사항) 3종 게시판과 댓글 기능을 제공합니다. 로그인 계정이 하나라도 있는 상태에서는 로그인해야 글쓰기/댓글이 가능하고, 계정이 하나도 없는 LAN 모드에서는 기존 데이터셋/테스트케이스 기능과 동일하게 인증 없이 전체 오픈됩니다.

1. 상단 서브탭에서 **일반/FAQ/VOC**를 선택 → 목록이 해당 게시판 글로 갱신됩니다.
2. "글쓰기"로 제목/내용을 입력해 등록. 글 제목을 클릭하면 상세+댓글 모달이 열립니다.
3. **권한 정책**: 글 삭제/댓글 삭제는 **관리자만** 가능합니다(VOC 등 민원 내용을 작성자가 임의로 지울 수 없도록 하는 정책). 글 수정과 노출/비노출 전환은 **작성자 본인 또는 관리자**가 할 수 있습니다.
4. 비노출로 전환한 글은 다른 사용자의 목록/상세에서 보이지 않습니다(작성자 본인과 관리자에게는 계속 보이며, 목록에 "비노출" 배지가 표시됨). 삭제와 달리 데이터는 남아있어 다시 노출로 되돌릴 수 있습니다.
5. **관리자 다중 선택 삭제**: 관리자 계정으로 보면 목록 왼쪽에 체크박스가 나타납니다. 여러 글을 체크한 뒤 "선택 삭제"를 누르면 한 번에 삭제됩니다(헤더 체크박스로 전체 선택 가능).
6. 댓글도 게시글과 동일하게, 비공개(비노출) 글에는 작성자·관리자만 댓글을 달 수 있습니다(다른 사용자는 그 글이 존재하는지조차 알 수 없음).
7. **데스크톱 앱 다운로드**: 게시판 탭 하단에 윈도우 설치형 앱(브라우저 없이 실행하는 pywebview 래퍼, 4.1절 참고)의 최신 `.exe` 파일을 바로 내려받을 수 있는 카드가 있습니다. 파일 크기와 최종 업데이트 날짜(`desktop_app/dist`의 실제 파일 수정일 기준)를 함께 보여주며, 서버에 새로 빌드한 `.exe`를 덮어쓰기만 하면 별도 설정 없이 자동으로 "최신"이 반영됩니다. 파일이 없으면 버튼이 비활성화되고 안내 문구가 표시됩니다.

### VOC 분석 탭

VOC 게시판 글을 자동으로 모아 LLM으로 분석해 개선안을 생성합니다. 필요하면 외부 소스를 추가하거나 분석 범위/관점을 좁힐 수 있습니다.

1. **게시판 VOC 글 포함(기본, 선택 해제 가능)**: 기본으로 체크돼 있어 아무것도 손대지 않으면 게시판 VOC 글로 분석합니다. Jira/엑셀만으로 분석하고 싶으면 체크를 해제할 수 있습니다.
2. **분석 지시사항(선택)**: "상담 대기시간과 불친절 관련 불만사항을 중심으로 정책 개선안을 제시해줘"처럼 특정 주제·관점으로 좁혀서 분석하고 싶으면 자유 텍스트로 입력합니다(최대 2,000자). 비워두면 전체 VOC를 종합 분석합니다. 이 지시사항은 "분석 관점을 좁히는 데이터"로만 취급되며, 이 안에 "이전 지시를 무시하고..." 같은 문구를 적어도 시스템 동작 자체를 바꾸지 못하도록 안전하게 분리되어 처리됩니다.
3. **분석 대상 건수(선택)**: 기본은 최신 150건이지만, "최근 20건만 요약해줘"처럼 더 적은 건수만 보고 싶으면 숫자를 입력합니다(1~150 범위, 항상 최신순).
4. **Jira 백로그 포함**: 체크 후 JQL을 직접 입력하거나(비우면 설정 탭에 저장된 프로젝트 키 기준 최신순 기본 쿼리 사용) "Jira 미리보기"로 실제 조회될 이슈 수를 먼저 확인할 수 있습니다. Jira 연동 정보(주소/이메일/토큰/프로젝트)는 설정 탭에 저장된 값을 그대로 사용합니다.
5. **엑셀/JSON 업로드 데이터 포함**: "엑셀 템플릿" 또는 "JSON 템플릿"으로 `source/date/category/content` 4개 컬럼(또는 필드) 양식(`.xlsx` 또는 `.json`만 지원)을 받아 채운 뒤 업로드합니다. **`date`(일자)는 선택 항목**이라 비워둬도 오류 없이 처리됩니다(정렬 시 항상 맨 뒤로 감). 업로드 후 몇 건이 인식됐는지, 업로드→완료 단계 체크리스트와 함께 표시됩니다. 업로드 파일은 5MB 이하만 허용되며, 파싱에 실패하면(JSON 문법 오류·최상위가 배열이 아님 등) 업로드된 파일이 서버에서 즉시 삭제됩니다.
6. "VOC 분석 실행"을 누르면 서버가 **백그라운드로 분석을 시작**하고 화면은 1.2초 간격으로 진행 상황을 자동 확인합니다(의도 분류 → 분석 생성 → 자가 재점검 → 독립 검증 → 저장 순차 실행, 통상 10~40초) - 이 5단계가 **단계별 체크리스트**로 실시간 표시되어 지금 어느 단계인지 바로 확인할 수 있습니다. 이 탭을 벗어나거나 새로고침해도 서버 쪽 작업은 안전하게 계속되고, **새로고침 후에도 진행 중이던 확인 화면이 자동으로 다시 이어집니다**(브라우저에 실행 ID를 임시 저장해두었다가 복원). 실행 중에는 "취소" 버튼으로 중단을 요청할 수 있으며, **이미 시작된 단계는 끝까지 처리되지만 아직 시작하지 않은 다음 단계로는 넘어가지 않습니다**(예: 개선안 생성까지는 끝났는데 취소를 누르면, 독립 검증은 더 이상 실행되지 않음). 항목당 500자까지만 반영되며, 실제 대상 건수는 결과 상단에 함께 표시됩니다.
   - **동시 실행 제한**: 계정(또는 공용 세션)당 한 번에 하나의 VOC 분석만 실행할 수 있습니다. 이미 실행 중인 분석이 있는 상태에서 다시 "VOC 분석 실행"을 누르면 실행되지 않고 안내 메시지가 표시됩니다 - 진행 중인 분석이 끝난 뒤 다시 시도하세요.
   - **개인정보(PII) 마스킹**: 내용에 전화번호·이메일·주민등록번호·카드번호·(계좌 안내 문구와 함께 쓰인) 계좌번호·여권번호·운전면허번호·IP주소가 섞여 있으면 분석에 넘어가기 전에 자동으로 부분 마스킹됩니다(예: `010-****-5678`). **다만 이 기능은 "완전한 개인정보 제거"를 보장하지 않는 제한적인 패턴(정규식) 기반 마스킹입니다.** 사람 이름·주소처럼 형태가 일정하지 않은 정보는 이 방식으로 신뢰성 있게 걸러낼 수 없어 대상에 포함되지 않으니, 민감한 내용은 가급적 VOC 원문 작성 단계에서부터 직접 유의해 주세요.
   - **일시적인 오류/서버 재시작 시**: 폴링 도중 네트워크 오류 등 일시적인 문제가 발생하면 자동으로 몇 차례 재시도하며, 계속 실패하면 버튼이 정상 상태로 복구되고 오류 메시지가 표시됩니다. 서버가 재시작돼 진행 중이던 작업 상태를 더 이상 찾을 수 없는 경우에도(예: 배포 중 재시작) 무한정 기다리지 않고 즉시 "서버 재시작 또는 작업 상태 만료" 안내와 함께 버튼이 정상 상태로 복구됩니다.
7. 결과에는 총평(summary)과 이슈별 빈도/심각도/개선안 표가 표시됩니다. LLM 응답이 예상 형식(스키마)을 벗어나면 자동으로 1회 재시도하고, 그래도 실패하면 안내 메시지로 우아하게 실패 처리됩니다.
8. 결과 하단에 **"독립 검증: PASS/FAIL/SKIPPED/ERROR"** 배지가 함께 표시됩니다. 개선안을 만든 모델이 스스로를 관대하게 채점하는 것을 막기 위해, 가능하면 **다른 provider의 모델**이 별도로 관련성/근본원인 대응/실행가능성/검증가능성 4개 기준 + 근거 id 실재 여부(결정적 검증)로 재심사합니다(자세한 구조는 [설계서](설계서.md) 6.7절 참고).
   - OpenAI/Anthropic 키가 **둘 다** 설정돼 있어야 실제 교차 검증(다른 모델로 검증)이 이뤄지며, 하나만 있으면 같은 모델로 폴백되고 "동일 모델로 검증(교차검증 아님)"이라고 정직하게 표시됩니다.
   - LLM이 설정되지 않았으면 "SKIPPED", 검증 호출 자체가 실패하면 "ERROR"로 표시됩니다(둘 다 통과로 위장하지 않음). ERROR가 나도 1단계 분석 결과 자체는 그대로 유지됩니다.
9. 분석 결과는 서버에 저장되어 **"VOC 분석 결과" 탭의 "지난 분석 이력"**에서 언제든 다시 볼 수 있습니다(서버 재시작에도 유지, 자동 만료 없음). **누가 실행했든 모든 실행자의 이력을 함께 볼 수 있습니다**(게시판/Jira 티켓과 동일하게 팀 공용 자료로 취급). 다만 삭제는 좁게 제한되어 **관리자 또는 그 분석을 실제로 실행한 본인**만 이력 목록의 "삭제" 버튼을 볼 수 있고, 그 외에는 남의 실행 결과를 지울 수 없습니다. **상세 보기 시 일부 항목은 실행자 본인/관리자에게만 표시됩니다**: 업로드 파일 경로는 누구에게도 표시되지 않고, Jira 조회 조건(JQL)과 분석 지시사항은 그 분석을 실행한 본인이나 관리자가 볼 때만 함께 표시되며 그 외 팀원에게는 해당 항목 자체가 보이지 않습니다(총평·이슈 표 등 분석 결과 본문은 기존과 동일하게 전원에게 공개).
10. LLM이 설정 탭에서 구성되어 있지 않으면 실행 시 안내 메시지가 표시됩니다 - 먼저 설정 탭에서 LLM 연동을 구성하세요.
10-1. **교차검증 매트릭스** ("교차검증 매트릭스 실행" 버튼, 분홍색): 위 8번의 "독립 검증"은 운영 실행마다 한 조합(생성 provider ↔ 반대쪽 provider)만 검증하지만, 이 버튼은 같은 데이터를 OpenAI/Anthropic 양쪽으로 각각 생성한 뒤 **A**(OpenAI 생성/Anthropic 평가) · **B**(Anthropic 생성/OpenAI 평가) · **C**(OpenAI 생성/OpenAI 평가, 동일 모델 대조군) · **D**(Anthropic 생성/Anthropic 평가, 동일 모델 대조군) 조합을 비교합니다. C/D가 A/B보다 관대한(PASS/APPROVED 쪽) 결과를 보이면 해당 모델이 자기 산출물을 스스로 채점할 때 편향될 수 있다는 신호로 해석할 수 있습니다. **OpenAI/Anthropic 키가 둘 다 설정돼 있어야** 실행할 수 있고(하나라도 없으면 안내 메시지), LLM 호출이 최대 6회(생성 2회+평가 4회)라 일반 VOC 분석보다 더 오래 걸립니다. 이 실행도 VOC 분석과 동일하게 **백그라운드 실행 + 단계별 진행사항 체크리스트**로 동작합니다 - "{provider} 생성 중" → "{조합} 조합 평가 중"(선택한 조합 수만큼, A~D 순서) → "저장 중" 단계가 실시간 표시됩니다(같은 백그라운드 실행 슬롯을 VOC 분석과 공유하므로, 둘 중 하나가 이미 실행 중이면 동시에 실행할 수 없습니다). 이 실행 결과는 일반 VOC 분석 이력과는 별도로 저장되며, **"VOC 분석 결과" 탭의 "지난 교차검증 매트릭스 이력"** 표에서 조합별(A~D) 품질게이트 요약을 확인하고 클릭해 상세 결과를 다시 볼 수 있습니다. 삭제는 일반 분석 이력과 동일하게 관리자 또는 그 매트릭스를 실행한 본인만 가능합니다.
    - **결과 화면**: 조합(A~D)마다 카드 형태로 요약(summary)·판정 배지(PASS/FAIL/ERROR/SKIPPED)·판정 근거(reasoning)·품질 게이트 상태를 함께 보여줍니다 - 일반 VOC 분석 결과(8번)와 완전히 동일한 배지·체크리스트·게이트 색상 컴포넌트를 그대로 재사용해 디자인이 일관됩니다. 예를 들어 지시사항에 맞는 근거를 찾지 못해 4개 조합 모두 FAIL로 나온 경우, "관련 근거가 없어 top_issues(개선안)가 비어 있습니다" 같은 근거 문구가 각 조합 카드에 바로 표시되어, 왜 실패했는지 저장된 원본 파일을 열어보지 않고도 화면에서 바로 확인할 수 있습니다.
    - **실행할 조합 선택**: 버튼 위 "실행할 조합 선택" 영역에서 A~D 체크박스로 이번에 실행할 조합을 고를 수 있습니다(기본은 4개 전부 체크). 최소 1개는 선택해야 하며, 아무것도 선택하지 않고 실행하면 안내 창이 뜨고 실행되지 않습니다. 일부만 선택하면 그 조합에 실제로 필요한 LLM 호출만 수행되어(예: A만 선택하면 OpenAI 생성 1회+Anthropic 평가 1회로 끝남) 그만큼 더 빨리, 더 적은 비용으로 끝납니다.
    - **이번 실행 전용 API 키**: 같은 영역의 "이번 실행에만 쓸 OpenAI/Anthropic API 키" 입력란에 키를 직접 입력하면, 설정 탭에 저장된 키 대신 이번 한 번의 실행에만 그 키를 사용합니다(비워두면 기존처럼 설정 탭의 키를 사용, 최대 300자). 여기 입력한 키는 서버에 저장되지 않고, 실행 이력(전원 공개)에도 절대 남지 않으며, 실행이 끝나면 성공/실패와 무관하게 입력란도 자동으로 비워집니다(같은 브라우저를 다음 사람이 쓰거나 화면을 오래 열어둬도 남지 않도록) - 팀 공용 서버에 개인 키를 저장하지 않고도 즉석에서 다른 키로 비교 실행해보고 싶을 때 사용하세요.
11. **"VOC 분석 결과" 탭**에는 이 기능의 실측치를 서버 API에서 매번 다시 계산해 보여주는 **품질 지표 차트**(테스트 총계/점검 범위/Judge 판정 분포/품질게이트 분포/결함 상태, 마크다운으로는 그래프를 그릴 수 없어 화면에 직접 그림 — pytest를 새로 돌리거나 VOC 분석을 실행하면 다음 새로고침에 바로 반영됨), 실제 구현·테스트 내용을 정리한 [VOC 분석 파이프라인 품질평가 보고서](VOC_분석_파이프라인_품질평가_보고서.md), 그리고 코드 리뷰에서 발견된 결함 상세를 담은 [VOC 분석 파이프라인 결함보고서](VOC_분석_파이프라인_결함보고서.md)가 "지난 분석 이력"/"지난 교차검증 매트릭스 이력"과 함께 순서대로 표시됩니다. 이 결함보고서는 대시보드 탭의 "결함보고서"(QA 파이프라인 실행 결과 자동 생성)와는 별개 문서입니다. 두 보고서 각각에는 **"개정 버전" 드롭다운**이 있어 문서의 실제 과거 개정본(git 커밋 이력 기반)을 선택해서 볼 수 있습니다 — "최신(현재)"가 기본값이고, 과거 버전을 선택하면 상단에 경고 문구가 함께 표시됩니다.
    - **차트 크게 보기(새 창)**: 품질 지표 차트 카드 오른쪽 위 버튼을 누르면 모니터링 애드온의 Prometheus/Grafana처럼 같은 차트를 **별도 페이지(`/voc-quality-chart`)로 새 창에서** 더 크게 볼 수 있습니다. 30초마다 자동 새로고침되며, 기존 화면/API에는 전혀 영향을 주지 않습니다.
    - **VOC 지표 Prometheus / Grafana(실제 연동)**: 위 품질 지표 차트는 "현재 값"만 보여주지만, 그 아래 카드에서는 **실제 Prometheus/Grafana**로 같은 지표(독립 Judge 판정 PASS/FAIL, 품질게이트 분포, 테스트 통과율)의 **추이(시계열)**를 볼 수 있습니다. Prometheus가 `/metrics-addon`을 15초 주기로 스크레이프하면서 자체적으로 시계열을 쌓으므로(모니터링 애드온의 서버 요청수 차트와 동일한 원리), 이 앱이 별도로 이력을 저장하지 않아도 시간에 따른 변화를 볼 수 있습니다. Prometheus 쿼리 결과는 이 페이지에 직접 그린 실시간 차트(PASS/FAIL 추이)로, Grafana 대시보드(`qa-platform-voc`, 6개 패널)는 iframe 임베딩으로 바로 보이고, 둘 다 새 창으로 여는 링크도 함께 제공됩니다. 11장의 Prometheus/Grafana 스택을 그대로 재사용하므로 **모니터링 애드온과 동일하게 `infra/docker-compose.monitoring.yml`(또는 전체 `docker compose up`)로 별도 실행해야** 보이며, `GRAFANA_LINK_ENABLED=false`면 이 카드 자체가 숨겨집니다.
    - **3000/9090 포트를 직접 열지 않고 접근**: 이 카드와 모니터링 애드온 페이지 모두 Grafana(3000)/Prometheus(9090) 포트에 브라우저가 직접 접속하지 않고, 이 앱의 `/grafana-proxy`·`/prometheus-proxy` 경로(로그인 필요)를 거칩니다. **AWS 등 공개 배포 시 보안그룹에서 3000/9090을 아예 열지 않고**, 아래 "접근 허용 IP" 관리자 탭에 등록된 IP/CIDR에서 접속할 때만 이 프록시가 통과됩니다(자세한 내용은 11-1절 참고).

### 모니터링 탭
QA 파이프라인 결과(대시보드 탭)와는 별개로, **이 서버 프로세스 자체의 운영 상태**를 봅니다.

1. **서버 운영 지표**: 가동시간, 총 요청 수, 에러율(5xx 기준), 평균/p95 응답시간, 헬스 상태를 카드로 표시
2. **최근 30분 요청 추이**: 분당 요청수를 선 그래프로, 에러가 발생한 분은 빨간 점으로 표시
3. **엔드포인트별 상세**: 최근 1시간 동안 요청이 많은 상위 10개 API 경로별 요청수/에러수/평균 응답시간
4. 탭이 열려 있는 동안 5초마다 자동 갱신되며, 서버를 재시작하면 지표는 초기화됩니다(디스크에 저장하지 않는 인메모리 집계 - Prometheus/Grafana 같은 외부 도구 없이 프로세스 하나의 상태만 보여주는 용도)

### 6.1.2 실행 탭

| 필드/버튼 | 목적 | 사용법 |
|---|---|---|
| 현재 테스트 케이스 표시 | 지금 실행하면 어떤 발화문 파일이 쓰이는지 확인 (데이터셋과는 별도 값) | 읽기 전용. "없음"이면 데이터셋 자체의 question이 그대로 쓰임 |
| 엑셀 양식 다운로드 버튼 | id/question 2열짜리 테스트 케이스 전용 템플릿 다운로드 | 데이터셋 템플릿과 다른, 훨씬 단순한 양식(정답 없음) |
| 미리보기 / 현재 파일 다운로드 버튼 | 지금 활성 테스트 케이스의 id/question 내용을 확인하거나 원본 파일을 내려받음 | 데이터셋 카드와 동일한 방식 |
| 파일 선택 + 테스트 케이스 업로드 버튼 | 실행 탭을 떠나지 않고 발화문 파일을 업로드 | 업로드하면 즉시 활성 테스트 케이스로 지정됨(버튼 아래 업로드→완료 단계 체크리스트 표시). id가 일치하는 데이터셋 케이스의 question만 덮어써서 실행됨 |
| 테스트 케이스 초기화 / 업로드 이력 | 활성 테스트 케이스 해제, 또는 과거에 올린 파일을 다시 선택 | 데이터셋 카드와 동일한 방식(초기화해도 이력은 안 지워짐) |
| 채점 기준 데이터셋 표시 | 지금 실행에 쓰일 데이터셋(정답)이 무엇인지 확인 (설정 탭과 같은 값 공유) | 읽기 전용 |
| 데이터셋 사용 안 함 체크박스 | 정답 비교 없이 테스트 케이스의 발화문만으로 품질 테스트 진행 | 켜면 category는 기본값(COM), golden_answer는 빈 값으로 처리되고, LLM 판정이 절대평가 모드로 자동 전환됨 |
| 테스트 기법 체크박스 | 이번 실행에서 어떤 채점 로직을 돌릴지 선택 (최소 1개 필수) | 아래 표 참고. 기본값은 `rag`+`llm_quality` |
| QA 파이프라인 실행 버튼 | 선택한 기법으로 활성 데이터셋 전체를 채점 | 클릭하면 서버가 백그라운드 스레드로 실행을 시작하고, 진행률 바가 완료될 때까지 자동으로 갱신됨(0.3초 간격 폴링) |
| CSV 다운로드 / 마크다운 다운로드 버튼 | 가장 최근 실행 결과를 파일로 저장 | 클릭 시 각각 `latest_report.csv/latest_report.md`가 새 탭에서 다운로드됨 |
| 진행률 바 / 상태 표시 / 단계 체크리스트 | 지금 실행이 대기/진행/완료/오류 중 어디에 있는지, 그리고 데이터 준비→평가 실행→리포트 저장→Jira 티켓 생성→(설정한 경우만) 알림 발송 중 어느 단계인지 시각적으로 확인 | 자동으로만 갱신되는 읽기 전용 표시 |
| 최근 실행 결과 | 방금 끝난 실행의 전체 리포트(JSON) 원문 확인 | 실행이 끝나면 자동으로 채워짐. `overall_pass_rate`, 케이스별 상세 점수 등을 그대로 볼 수 있음 |
| 불일치 및 기능 테스트 | 룰 판정과 LLM 판정이 갈린 케이스(`mismatch_cases`), 커넥터 계약 검사 결과(`functional_test`), 룰-API 비교 집계(`rule_api_comparison`), 회귀 발생 건수(`regressions_detected`)를 별도로 확인 | 실행이 끝나면 자동으로 채워짐. 특히 `dual_compare/functional` 기법을 선택했을 때 확인할 내용이 여기 담김 |

#### 테스트 기법별 목적

| 기법 | 목적 |
|---|---|
| `rag` | 검색품질(Recall/Precision/MRR) + 근거성(환각 탐지) + 컨텍스트 관련성 평가 |
| `llm_quality` | LLM이 정확성/관련성/일관성/유해성을 1~5점으로 채점(LLM-as-a-Judge) |
| `rubric` | 사용자가 정의한 가중치 채점표(criteria)로 LLM이 채점 |
| `regression` | 골든 답변과의 문자열 유사도로 회귀(이전엔 통과했는데 이번엔 실패) 여부 확인 |
| `functional` | 빈 질문/공백/과도하게 긴 질문/특수문자 등 4가지 합성 질문으로 커넥터가 계약대로 동작하는지 검사 (케이스 데이터셋과 무관하게 실행당 1회) |
| `dual_compare` | 데이터셋에 저장된(룰) 답변과 이번 실행의 실시간 응답을 나란히 비교 |
| (항상 실행) 유해성 검사 | 기법 선택과 무관하게 금칙어/PII 패턴을 항상 검사하는 안전 가드레일 |

### 6.1.5 외부 서비스 모니터링 상세

위 표의 마지막 항목을 더 자세히 설명합니다. 이 기능은 QA 파이프라인의 `api` 커넥터 모드(6.1.2절)와는 완전히 별개입니다 — 커넥터 모드는 테스트 케이스를 채점할 때 1회성으로 호출하는 것이고, 여기는 **서버가 백그라운드에서 계속 반복 호출**하며 살아있는지만 확인합니다.

| 입력값 | 설명 |
|---|---|
| 이름 | 목록에서 구분하기 위한 표시용 이름 (임의 문자열) |
| URL | 체크할 대상 주소. `http://` 또는 `https://`로 시작해야 하며, 아니면 등록이 거부됨 |
| Method | `GET` 또는 `POST` 중 선택 (대상 서비스가 요구하는 방식에 맞춤) |
| 체크 주기(초) | 몇 초마다 다시 호출할지. 최소값은 10초이며, 이보다 작게 입력해도 서버가 자동으로 10초로 올림(대상 서비스에 과도한 부하를 주지 않기 위함) |

동작 방식:

1. 대상을 등록하면 서버 시작 시부터 계속 돌고 있는 백그라운드 스레드가 해당 URL을 즉시 1회, 이후로는 설정한 주기마다 반복 호출합니다.
2. 응답이 2xx~3xx면 "정상", 그 외 상태코드나 타임아웃/연결 실패면 "실패"로 기록됩니다.
3. "가동률(최근 20회)"은 최근 20번 체크 중 성공 비율, "최근 응답"은 가장 최근 체크의 응답시간입니다.
4. 등록된 대상 목록은 `reports/monitoring_targets.json`에 저장되어 서버를 재시작해도 유지되지만, 체크 이력(가동률/응답시간 추이)은 서버 운영 지표와 마찬가지로 메모리에만 있어 재시작하면 초기화됩니다.

## 11. 모니터링 애드온 (k6 성능테스트 / SQLite 이력 / Prometheus·Grafana)

기존 플랫폼(1~10장)과 완전히 분리된 확장 기능입니다 - 기존 `MetricsCollector`, 미들웨어,
`/api/monitoring/summary` 응답 구조, 기존 모니터링 화면은 이 기능 때문에 전혀 바뀌지
않습니다. 실행/롤백 방법을 포함한 전체 내용은 이 장에 정리되어 있습니다 — 프로젝트 최상위
[README.md](../README.md)는 같은 내용을 담은 간단한 기술 참고용 요약이며, 사용자 기준
공식 참고 문서는 이 사용자 매뉴얼입니다.

이 장에서 설명하는 Prometheus/Grafana 스택은 **VOC 분석 품질 지표**도 함께 시각화합니다 -
다만 그 화면은 이 `/monitoring-addon` 페이지가 아니라 **메인 대시보드의 "VOC 분석 결과"
탭**(6장 참고)에 있습니다. 실행/설정 방법(아래 "Prometheus / Grafana 실행")은 완전히
동일하므로 별도로 반복하지 않습니다.

### 접근 방법

- 기존 대시보드의 "모니터링" 탭 상단에 있는 "성능 테스트(k6)·Prometheus 연동 대시보드 보기 →"
  링크를 클릭하거나, `http://localhost:8000/monitoring-addon`으로 직접 접속합니다.
- 완전히 별도 페이지라서, 이 페이지의 어떤 동작도 기존 대시보드 화면에 영향을 주지 않습니다.

| k6 성능테스트 실행 | 대상 URL/동시사용자수/지속시간을 입력해 웹 화면에서 바로 k6를 실행 (아래 "웹에서 직접 k6 실행" 참고) |
| k6 최신 성능테스트 결과 | 가장 최근 k6 실행의 실행 ID/대상/동시사용자수/총 요청수/실패율/평균·p95 응답시간/Pass·Fail 판정 |
| 실행별 p95 응답시간 추이 | 최근 실행들의 p95 응답시간을 선 그래프로 비교 |
| k6 실행 이력 | 여러 번의 k6 실행을 최신순으로 나열, Pass/Fail 필터와 페이지네이션 제공, "상세" 버튼으로 threshold별 통과 여부 확인 |
| 운영 지표 장기 스냅샷 | 기존 `MetricsCollector` 요약값을 1분 주기로 읽기 전용 저장한 이력 (재시작 전까지 누적) |
| Prometheus 쿼리 | Prometheus `/graph` 화면이 iframe으로 페이지에 직접 임베딩되어 실시간 쿼리 결과를 바로 볼 수 있음(별도 설정 불필요) + 새 창으로 여는 링크 제공 |
| Grafana 대시보드 | Grafana 대시보드의 6개 패널이 iframe으로 페이지에 직접 임베딩되어 실시간으로 보임(Grafana를 따로 열 필요 없음) + 새 창으로 직접 여는 링크도 함께 제공 (`GRAFANA_LINK_ENABLED=false`면 Prometheus/Grafana 섹션이 모두 숨겨짐) |

각 영역은 데이터를 개별적으로 불러오기 때문에, 예를 들어 k6 실행 이력이 아직 없어도 다른
영역(운영 지표 스냅샷 등)은 정상적으로 보입니다 - 한 영역의 오류가 페이지 전체를 깨뜨리지
않습니다.

### 웹에서 직접 k6 실행

`/monitoring-addon` 페이지의 "k6 성능테스트 실행" 카드에서 대상 URL, 동시사용자수(1~50),
지속시간(10초~2분 중 선택)을 입력하고 "실행" 버튼을 누르면 서버가 백그라운드에서 k6를
실행합니다. 실행 중에는 상태가 2초마다 자동 갱신되어 **진행률 바**(경과시간÷지속시간 기준
%)와 **단계 체크리스트**(요청 시작 → 부하 테스트 진행 중 → 완료)로 지금 어디까지 왔는지
시각적으로 표시되며, 완료되면 위의 "k6 최신 성능테스트 결과"와 "k6 실행 이력"이 자동으로
새로고침됩니다.

- **대상 URL은 localhost 또는 사내망 IP(10.x/172.16-31.x/192.168.x)만 허용됩니다** - 외부
  인터넷 주소를 입력하면 400 에러로 거부됩니다. 이 웹 버튼이 임의의 외부 서버에 부하를
  거는 도구로 악용되는 것을 막기 위한 제한입니다.
- 한 번에 하나의 실행만 허용됩니다 - 이미 실행 중일 때 다시 누르면 "이미 실행 중인
  성능테스트가 있습니다" 에러가 표시됩니다.
- 서버에 `k6` 실행 파일이 PATH에 설치되어 있어야 합니다 (없으면 안내 메시지가 표시됨).
- 페이지를 새로고침해도 실행 중이던 작업의 진행 상황이 그대로 이어서 표시됩니다.

CLI로 직접 실행하고 싶다면 아래 방법도 그대로 사용할 수 있습니다(둘은 같은 스크립트를
공유하며, CLI 실행에는 위의 URL/시간 제한이 적용되지 않습니다):

```bash
k6 run tests/k6/load_test.js
```

실행이 끝나면 자동으로 `reports/k6/latest.json`(과 `reports/k6/history/{run_id}.json`)이
생성되고, `/monitoring-addon` 페이지를 새로고침(또는 최신 결과 조회)하면 서버가 알아서
SQLite에 저장한 뒤 보여줍니다. 서버 없이 바로 DB에 넣고 싶으면 `python scripts/import_k6_result.py`를
실행합니다. 대상 URL/VU 수/지속시간은 환경변수로 바꿀 수 있습니다:

```bash
LOAD_TARGET_URL=http://localhost:8000 LOAD_VUS=20 LOAD_DURATION=1m k6 run tests/k6/load_test.js
```

### Prometheus / Grafana 실행

**방법 1 - 전체를 Docker로 (권장)**: 4장 "Docker 실행"의 `docker compose up -d --build` 한
번으로 앱과 함께 Prometheus/Grafana도 같이 뜹니다. 이미지에 k6 실행 파일도 포함돼 있어
"웹에서 직접 k6 실행" 기능도 컨테이너 안에서 그대로 됩니다. 종료는 `docker compose down`.

**방법 2 - 앱은 로컬에서 직접(`uvicorn`) 띄우고, Prometheus/Grafana만 Docker로**: 기존
`docker-compose.yml`(FastAPI 앱)과 완전히 별개인 전용 compose 파일을 씁니다.

```bash
docker compose -f infra/docker-compose.monitoring.yml up -d
```

- Prometheus: `http://<서버 IP>:9090` (Targets 메뉴에서 `ai-agent-monitoring-addon` job이 UP인지 확인)
- Grafana: `http://<서버 IP>:3000` - Prometheus 데이터소스와 "QA Platform Monitoring Addon"
  대시보드가 자동으로 provisioning되어 있습니다. 익명 Viewer 접속이 켜져 있어 로그인 없이
  바로 보이며(admin/admin으로 직접 로그인도 가능), `/monitoring-addon` 페이지에는 이
  대시보드의 6개 패널이 iframe으로 직접 임베딩되어 있어 Grafana를 따로 열지 않아도
  실시간 그래프를 바로 볼 수 있습니다.
- 종료: `docker compose -f infra/docker-compose.monitoring.yml down`

**방법 3 - 앱도 로컬 프로세스로 두고, Prometheus/Grafana도 스크립트 하나로**: Docker로
Prometheus/Grafana를 먼저 기동한 뒤 이어서 같은 프로세스에서 FastAPI 앱을 실행합니다.
Docker가 없거나 꺼져 있어도 Prometheus/Grafana만 조용히 건너뛰고 앱은 정상적으로 뜹니다
(1번의 "서버 실행" 대신 사용):

```bash
python scripts/start_platform.py
```

### Feature Flag (`.env`)

모두 기본값 `true`(opt-out 방식)라 별도 설정 없이 바로 동작합니다.

| 변수 | 기본값 | 끄면 어떻게 되는지 |
|---|---|---|
| `MONITORING_ADDON_ENABLED` | true | 애드온 라우터/스레드/페이지 전체가 등록되지 않음 (`/monitoring-addon, /api/monitoring-addon/*, /metrics-addon` 전부 404) |
| `K6_HISTORY_ENABLED` | true | `k6/runs, k6/runs/{id}` 이력 조회만 비활성(`/k6/latest`는 파일을 직접 읽어 계속 동작) |
| `MONITORING_ADDON_DB_ENABLED` | true | SQLite 저장/조회 전부 비활성 - 스냅샷 스레드도 시작하지 않음 |
| `PROMETHEUS_ADDON_ENABLED` | true | `/metrics-addon` 라우터 자체를 등록하지 않음 |
| `GRAFANA_LINK_ENABLED` | true | `/monitoring-addon` 페이지에서 Prometheus/Grafana 링크 섹션을 숨김 |

### Grafana/Prometheus 프록시 설정 (`.env`, 값 지정형)

위 Feature Flag와 달리 값을 직접 채우는 설정입니다 - 셋 다 비워두면 로컬/LAN 기본값을 씁니다.

| 변수 | 기본값(비워둘 때) | 용도 |
|---|---|---|
| `GRAFANA_ROOT_URL` | `http://localhost/grafana-proxy/` | Grafana가 `/grafana-proxy` 서브패스로 서빙되도록 하는 실제 공개 주소. AWS 등 공개 배포 시 실제 도메인으로 바꿔야 정적 리소스(JS/CSS)가 정상 로드됨(예: `https://your-domain.com/grafana-proxy/`) |
| `GRAFANA_INTERNAL_URL` | `http://grafana:3000` | 이 앱(qa-platform)이 Grafana 컨테이너에 접근할 내부 주소. 같은 `docker-compose.yml`로 함께 띄우면 기본값 그대로 사용 |
| `PROMETHEUS_INTERNAL_URL` | `http://prometheus:9090` | 이 앱이 Prometheus 컨테이너에 접근할 내부 주소. 앱을 로컬 uvicorn으로 별도 실행한 경우(`infra/docker-compose.monitoring.yml` 사용 시)에는 `http://localhost:9090`으로 바꿔야 함 |

### 끄고 싶을 때 (롤백 절차)

1. `.env`에 `MONITORING_ADDON_ENABLED=false` 추가
2. 서버 재시작 - 애드온 라우트가 전부 사라지고(`/monitoring-addon`, `/api/monitoring-addon/*`,
   `/metrics-addon`이 전부 404) 1~10장에서 설명한 기존 플랫폼은 아무 영향 없이 그대로 동작
3. 그래도 문제가 있으면 `monitoring_addon/`, `app/routers/monitoring_addon.py`,
   `app/templates/monitoring_addon.html`을 삭제
4. `data/monitoring_addon.db`(및 `-wal`/`-shm`) 삭제 (Docker로 띄운 경우 `docker volume rm ai_agent_quality_portfolio_qa-platform-data`)
5. `docker compose down`(전체 스택) 또는 `docker compose -f infra/docker-compose.monitoring.yml down`(Prometheus/Grafana만 따로 띄운 경우)으로 컨테이너 정리
6. 기존 `/`, `/api/monitoring/summary`, 기존 QA 파이프라인 API가 정상인지 확인
