# 프로세스 명세서

| 항목 | 내용 |
|---|---|
| 문서 목적 | QA 파이프라인 실행 프로세스를 단계별로 상세히 기술 |
| 관련 문서 | [설계서](설계서.md) (아키텍처/데이터모델), [사용자_매뉴얼](사용자_매뉴얼.md) (사용법) |

> 각 단계에 담당 파일:함수를 명시했습니다. 파이프라인 로직을 변경했다면 이 문서의 해당 단계도 함께 갱신하세요. `tests/test_docs_reference_integrity.py`가 아래 언급된 파일/함수가 실제로 존재하는지 자동 검사합니다.

---

## 1. 표준 실행 프로세스 (웹 `POST /api/run`)

```
1. 클라이언트가 POST /api/run 호출
   { techniques[], mode?, api_endpoint?, category?, openai_api_key?,
     dataset_path?, jira_config?, slack/discord/teams_webhook_url? }
        │
        ▼
2. app/main.py::run_pipeline
   - techniques 검증 (비어있으면 400, ALL_TECHNIQUES에 없는 값이면 400)
   - run_id 발급, RUN_REGISTRY[run_id] = {status: "queued", progress: {0,1}}
   - daemon Thread로 _execute_run() 실행, 즉시 {run_id, status} 응답
        │
        ▼ (백그라운드 스레드)
3. app/main.py::_execute_run
   - status = "running"
   - 데이터셋 로드: dataset_path 지정 시 그 경로, 아니면 ACTIVE_DATASET,
     둘 다 없으면 _default_cases()의 데모 케이스 1건
   - Config(reports_dir="reports") 생성 후 connector/openai 설정 오버라이드
   - PipelineOrchestrator(config).run(cases, category_filter, techniques,
     run_id, on_progress) 호출
        │
        ▼
4. qa_agent/pipeline.py::PipelineOrchestrator.run
   4-1. "regression" 기법 포함 시 _load_previous_pass_map(run_id)로
        가장 최근 run_*.json에서 케이스별 이전 pass 여부를 로드
   4-2. ThreadPoolExecutor(parallel_workers)로 케이스마다
        _evaluate_case()를 병렬 실행, 완료마다 on_progress(idx, total) 호출
   4-3. 결과를 원래 데이터셋 순서로 재정렬 (스레드 완료 순서는 비결정적이므로)
   4-4. "functional" 기법 포함 시 _run_functional_test() 1회 실행
        (케이스와 무관, 커넥터 계약 검사)
   4-5. _build_report()로 RunReport 조립
   4-6. _write_reports()로 reports/run_{id}.json, reports/latest.json 저장
        │
        ▼
5. app/main.py::_execute_run (계속)
   - qa_agent.reporter.write_reports(report) → run_{id}.json/.csv,
     latest.json, final_quality_report.md (reports/ + reports/exports/)
   - qa_agent.reporter.write_defect_report_doc(report) → docs/결함보고서.md
   - no_jira가 아니면 JiraNotifier(...).notify(report) → 카테고리별 실패율
     초과 시 티켓 생성, 생성됐다면 reports/jira_{run_id}.json에 저장
   - 웹훅 URL이 지정된 알림 채널에 SlackNotifier/DiscordNotifier/
     TeamsNotifier.notify(report) 호출
   - RUN_REGISTRY[run_id] = {status: "done", result: report.to_dict()}
     (예외 발생 시 status: "error", error: str(exc))
        │
        ▼
6. 클라이언트가 GET /api/run/{run_id}/status를 폴링(대시보드는 0.3초 간격)
   status가 done/error가 되면 GET /api/run/{run_id}/result로 전체 리포트 조회
```

## 2. 케이스 1건 평가 세부 흐름 (`_evaluate_case`)

```
GoldenCase
   │
   ▼
_get_response(case)  ── 커넥터 모드에 따라 분기 ──┐
   │                                            │
   ├─ dataset_only: existing_answer 재사용        │
   ├─ mock: "[mock] {golden_answer}" 고정 반환    │
   └─ api: HTTP 호출 → {answer, contexts, doc_ids} │
   │                                            │
   ▼                                            │
ChatbotResponse ◄───────────────────────────────┘
   │
   ├─ response.error 있음
   │     → errors.append(error), overall_pass=False, 즉시 반환 (평가 전부 스킵)
   │
   └─ response.error 없음
        │
        ├─ [rag] 기법 선택 시
        │     - relevant_doc_ids 있으면 RetrievalEvaluator
        │     - GroundednessEvaluator (컨텍스트 없으면 trivial pass)
        │     - ContextRelevanceEvaluator (컨텍스트 없으면 trivial pass)
        │
        ├─ [llm_quality] 기법 선택 시
        │     - LLMJudgeEvaluator (OPENAI_API_KEY 없으면 errored=True,
        │       overall_pass 판정에서 제외)
        │
        ├─ [rubric] 기법 선택 시
        │     - RubricEvaluator (동일하게 errored 시 제외)
        │
        ├─ [regression] 기법 선택 시
        │     - RegressionEvaluator (룰: SequenceMatcher 유사도,
        │       룰 실패 시에만 LLM 의미 동등성 판정 추가 호출)
        │     - is_regression = 직전 실행에서 pass였는데 이번에 fail이면 True
        │
        ├─ (항상 실행) ToxicityEvaluator
        │     - 금칙어/PII 룰 검사 + LLMJudgeResult.toxicity 재사용
        │
        ├─ [dual_compare] 기법 선택 + existing_answer 있으면
        │     - _evaluate_dual_compare(): 이미 받은 response를 재사용해
        │       rule_answer(existing_answer) vs api_answer(response.answer)
        │       각각 키워드 검증 + LLM 4점 채점 → comparison_status 산출
        │       (BOTH_PASS/BOTH_FAIL/API_ONLY_PASS/RULE_ONLY_PASS)
        │
        ▼
   overall_pass = AND(선택되어 실행된 항목들의 pass 여부)
```

## 3. 리포트 집계 프로세스 (`_build_report`)

```
케이스별 CaseResult 리스트
   │
   ├─ category_stats: GoldenCase.category별 total/passed 집계
   ├─ overall_pass_rate: passed 케이스 수 / 전체 케이스 수
   ├─ regressions_detected: regression.is_regression=True인 케이스 수
   ├─ comparison_summary: groundedness/context_relevance/regression/toxicity의
   │  agreement(match/mismatch) 집계
   ├─ mismatch_cases: agreement=mismatch인 케이스 목록 (case_id, rule_passed, llm_passed)
   ├─ functional_test: _run_functional_test() 결과 (technique 미선택 시 빈 dict)
   └─ rule_api_comparison: dual_compare의 comparison_status별 건수
   │
   ▼
RunReport 조립 → reporter.write_reports() → JSON/CSV/MD 저장
```

## 4. 예외/에러 처리 원칙

| 상황 | 처리 |
|---|---|
| 커넥터 호출 실패(네트워크/JSON 파싱) | `ChatbotResponse.error` 세팅, 해당 케이스는 평가 스킵하고 `overall_pass=False` — 품질 실패가 아니라 인프라 실패로 별도 표기 |
| OpenAI 호출 실패/키 없음 | 해당 평가 결과에 `errored=True` 세팅, `overall_pass` 판정에서 그 항목 제외 (파이프라인 전체는 계속 진행) |
| Jira 티켓 검색 API 실패 | 중복 생성을 피하기 위해 안전하게 티켓 생성을 건너뜀 |
| 백그라운드 실행 중 예외 | `RUN_REGISTRY[run_id]`에 `status="error"`, `error=str(exc)` 기록. 스레드가 죽어도 API는 계속 응답 가능 |

## 5. 테스트 실행 프로세스 (품질 관리 자동화)

```
pytest 실행
   │
   ▼
conftest.py::_no_real_secrets_in_tests (autouse)
   - OPENAI_API_KEY 등 실제 비밀값을 테스트마다 강제로 비움
   │
   ▼
각 테스트 실행
   │
   ▼
conftest.py::pytest_terminal_summary
   - quality/test_report.py::write_test_results_doc() 호출
   - docs/테스트_결과.md 자동 재생성
```

## 6. 문서 현행화 프로세스

```
QA 파이프라인 실행 완료 (app/main.py::_execute_run)
   → qa_agent/reporter.py::write_defect_report_doc()
   → docs/결함보고서.md 자동 재생성

pytest 실행 완료 (아무 조건 없이 매번)
   → conftest.py::pytest_terminal_summary
   → docs/테스트_결과.md 자동 재생성

수동 관리 문서(사용자_매뉴얼.md/설계서.md/프로세스_명세서.md)
   → tests/test_docs_reference_integrity.py가 문서에 적힌 파일 경로/
     식별자가 실제 코드에 존재하는지 pytest 실행 시마다 검증
   → 실패하면 문서가 코드와 어긋났다는 신호이므로 사람이 갱신
```
