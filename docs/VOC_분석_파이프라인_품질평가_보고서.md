| 03. Summarizer (요약) | ✅ 구현됨* | `build_prompts()` + 생성 LLM **1회 호출**로 요약 생성 (*별도 모듈 아님, 04 Improver와 동일 호출) |

Evaluator / Critic / Refine (자가 루프) | ✅ **구현됨(4차 개정)** | `_self_check_and_refine()`/`build_refine_prompt()` — 생성에 쓴 같은 모델이 자기 결과를 재점검(08과 동일 메커니즘 공유)하고 `FAIL`이면 그 criteria/reasoning을 피드백 삼아 **딱 1회만** 재작성(무한 루프·비용 폭주 방지 상한). 재작성도 기존 스키마·근거ID 검증을 동일하게 통과해야 채택되며, 실패하면 원본 결과를 그대로 보존(`after_verdict="REFINE_FAILED"`로 정직 표시) |
| 07. Improver (개선안 생성) | ✅ 구현됨* | Summarizer와 동일 호출에서 `top_issues`(개선안) 동시 생성. 04~06의 재작성(refine)도 이 스키마를 그대로 재사용 |
| 08. Evaluator/Critic (내부 재점검) | ✅ **구현됨(4차 개정)** | `_self_check_and_refine()`이 `run_independent_judge()`를 `judge_client=generation_client, cross_model=False`로 재사용 — 같은 모델의 자기 재점검임을 항상 정직하게 표시(신규 코드 없이 기존 스키마/근거ID 검증 로직 재활용). 독립 Judge(09)와 목적이 다른 별개의 값싼 1차 방어선 |
| 09. 독립 LLM Judge | ✅ **구현·실증됨** | `run_independent_judge()` — 생성과 실제로 다른 provider로 재검증(아래 2장 실제 사례) |
| 10. 최종 판정 | ✅ 구현됨* | `PASS / FAIL / SKIPPED / ERROR` 4단계(*템플릿은 2단계만 전제 — 검증 불가 상태를 통과로 위장하지 않기 위해 세분화) |

> **4차 개정 실증**: 01/04~06/08 모두 실제 OpenAI(생성/Interpreter/내부재점검) + Anthropic(독립 Judge) 호출로 종단 검증했습니다. 04~06의 FAIL→재작성→성공, 재작성 스키마 위반 시 원본 보존 두 경로는 결정론적 fake 클라이언트로 정확히 재현해 회귀 테스트 4건으로 고정했고(실제 LLM은 매 호출 응답이 달라 특정 실패 경로를 안정적으로 강제할 수 없음), 08/09는 동일 세션에서 실제 API로 `self_check`/`judge` 필드가 채워짐을 직접 확인했습니다.

### ★ 실제 구현한 핵심 차별화 요소 — 자기평가 편향 배제 (실증 완료)

`app/main.py::_independent_judge_kwargs()`가 생성에 쓴 provider와 **가능하면 반대 provider**를 독립 검증용으로 선택합니다. 두 provider의 키가 모두 없으면 같은 provider로 폴백하되 `cross_model: false`로 정직하게 노출합니다.

**1차 코드 리뷰에서 발견된 실제 결함**: `_independent_judge_kwargs`가 provider를 anthropic으로 전환하면서도, 생성(openai)용으로 설정된 `llm_model`("gpt-4o-mini")을 그대로 들고 있어 Anthropic API에 존재하지 않는 모델명을 요청 → **404 Not Found**가 발생하고 있었습니다. 수정 후에도 Anthropic의 최신 모델(claude-sonnet-5, 확장 사고 모델)이 `temperature` 파라미터 자체를 거부(`400 temperature is deprecated for this model`)하는 2차 문제가 있어 함께 수정했습니다. 두 결함을 모두 고친 뒤 실제로 Anthropic이 독립 심사관 역할을 정상 수행함을 확인했습니다(아래 2장).

## 3. 파이프라인 3단계 구성과 정량 분석

### 3.0 실제 3단계 구성

| 단계 | 내용 | 실제 구현 |
|---|---|---|
| **1단계** | VOC 분석 및 정책 개선안 생성 | `_generate_analysis()` — 게시판/Jira/엑셀 데이터를 정규화해 생성 LLM 1회 호출, summary+top_issues 생성 |
| **2단계** | 내부 품질 진단(결정적 검증) | `validate_analysis_schema()` — LLM 출력 스키마(타입/개수/범위) 검증, 위반 시 1회 재시도. **템플릿이 말하는 "6개 멀티 에이전트"는 아니며, 코드 기반의 단일 결정적 게이트입니다** — 이 차이를 숨기지 않습니다 |
| **3단계** | 독립 LLM Judge 평가 | `run_independent_judge()` — 생성과 다른 provider로 4가지 의미 기준 + `example_ids_valid`(결정적) 채점 |

### 3.1 역할 구분 — 결정적 검증(2단계) vs 독립 Judge(3단계)

템플릿은 Evaluator·Critic이라는 별도 LLM 에이전트를 상정하지만, 실제로는 **코드 기반 결정적 검증**과 **LLM 기반 의미 검증**이라는 두 개의 서로 다른 성격의 게이트로 그 역할을 나눠 구현했습니다.

| 구분 | 무엇을 하는가 | 실행 주체 | 실패 시 |
|---|---|---|---|
| 2단계(Evaluator 역할에 해당) | 출력이 스키마를 지키는가(타입, 개수, 범위) | 코드(`validate_analysis_schema`/`validate_judge_schema`) — LLM 아님 | 1회 재시도 후 안전 실패(502) |
| 3단계(Critic+Judge 역할에 해당) | 내용이 실제로 타당한가(관련성/근본원인/실행가능성/측정가능성) + 근거 id가 실재하는가 | 생성과 다른 LLM + 코드(`example_ids_valid`) | `FAIL`로 표시(결과는 숨기지 않고 그대로 노출) |

이 두 게이트가 성격이 다른 이유: 스키마 위반(예: frequency가 문자열)은 "형식 오류"라 코드로 100% 결정적으로 잡을 수 있지만, "이 개선안이 실제로 타당한가"는 의미 판단이라 결정적 코드로는 불가능합니다 — 그래서 3단계만 LLM에 맡기고, 2단계는 의도적으로 LLM을 쓰지 않았습니다(비용·속도·신뢰성 모두 이 편이 유리).

### 3.3 결함관리 내역 — 분기 인터페이스 오류 · API 호환성 오류

코드 리뷰에서 지적된 항목 중, 실제로 운영 환경에서 재현·수정까지 완료한 2건의 API 연동 결함입니다(사전에 짐작한 원인이 아니라 실제 로그로 근본 원인을 확인).

| 오류 유형 | 증상 | 근본 원인 | 수정 |
|---|---|---|---|
| Provider 분기 인터페이스 오류 | 독립 Judge가 Anthropic으로 전환됐는데도 `404 Not Found` | `_independent_judge_kwargs`가 생성(openai)용 `llm_model`("gpt-4o-mini")을 그대로 물려줘 Anthropic에 존재하지 않는 모델을 요청 | provider가 실제로 바뀌면 오염 가능 필드(`llm_model`/`llm_key_value` 등) 제거 |
| API 파라미터 호환성 오류 | 1차 수정 후에도 `400 temperature is deprecated for this model` | Anthropic의 확장 사고 모델(claude-sonnet-5)이 `temperature` 파라미터 자체를 거부 | Anthropic 요청 페이로드에서 `temperature` 제거 |

> 참고: 흔히 발생하는 `429`(rate limit) 오류는 이번 검증 과정에서 **발생하지 않았습니다** — 실제로 발생한 오류는 위 표의 404/400이며, 추측이 아니라 `docker exec`로 직접 재현한 실제 HTTP 응답 본문을 근거로 진단했습니다.

## 4. 이번 코드 리뷰에서 발견·수정한 결함 (P0 7건 + P1 6건)

독립적인 코드 리뷰를 거쳐 발견된 결함을 전부 실제 코드 수정 + 회귀 테스트로 대응했습니다. **결함 항목별 상세(근본 원인·수정 내용·회귀 테스트)는 이 보고서와는 별개 문서인 [`VOC_분석_파이프라인_결함보고서.md`](VOC_분석_파이프라인_결함보고서.md)에 정리했습니다** — AI Agent 품질관리 플랫폼의 핵심 QA 파이프라인이 자동 생성하는 `결함보고서.md`(실행 ID 기준)와는 대상·발견 방식이 전혀 다른 별개 업무이므로 문서도 분리했습니다.

| 구분 | 건수 | 요약 |
|---|---|---|
| 1차 P0(즉시 수정) | 7건 | Judge 근거 검증 부재, provider 혼용(404 원인), 업로드 보안, 댓글 권한 우회, XSS, 분석 ID 충돌, 삭제 정책 부재 |
| 1차 P1(품질 개선) | 6건 | 출력 스키마 미검증, 오류 메시지 노출, 프롬프트 인젝션, `.xls` 광고-실패 불일치, 취소 수단 부재, 게시판 다중삭제 부재 |
| 2차 P0(즉시 수정) | 4건 | 전체 테스트의 실제 운영 데이터 오염, quality_gate 도입 후 실증 공백, 감사 증적 테스트 수 불일치, 보고서 과장 표현 |
| 2차 P1(품질 개선) | 2건 | 품질 차트 정적 고정값(3차 개정에서 API 기반 완전 동적화), 빈 top_issues UX 불명확(수정 완료) |

### 신규 기능 요청 반영

| 요청 | 반영 내용 |
|---|---|
| 게시판 VOC 포함 여부를 Jira/엑셀과 별도로 선택 | `use_board`(기본 true) 파라미터 분리 — 아무것도 선택 안 하면 게시판 VOC, Jira/엑셀 선택 시 게시판 포함 여부 별도 지정 가능 |
| 일반/FAQ/VOC 목록에서 관리자 다중 선택 삭제 | `POST /api/board/posts/bulk-delete`(관리자 전용) + 체크박스 UI |
| VOC 분석 결과 이력 관리 | `DELETE /api/voc-analysis/{id}`(4차 개정: 관리자 전용 → **관리자 또는 그 분석을 실행한 본인**) + 이력 목록 삭제 버튼. 조회(`GET /history`/`GET /{id}`)는 4차 개정에서 실행자 격리를 폐지하고 게시판·Jira 티켓과 동일하게 **전원 공개**로 전환 |

## 5. 왜 해당 개선안이 타당한가 — 독립 Judge의 4가지 기준 (+결정적 검증 1가지)

`build_judge_prompts()`가 강제하는 판정 기준입니다. 4개 중 하나라도 false면 `verdict: FAIL`이며, **`example_ids_valid`(결정적 검증)가 false면 LLM이 뭐라 답했든 강제로 FAIL로 덮어씁니다.**

| 기준 | 판단 내용 | 검증 방식 |
|---|---|---|
| `relevance` | 개선안이 원본 불만과 실제로 연계되는가 | LLM 의미 판단(2장 시나리오 1·3에서 실제로 부적합을 잡아냄) |
| `root_cause_addressing` | 표면 증상이 아니라 근본 원인에 대응하는가 | LLM 의미 판단 |
| `feasibility` | 대상/우선순위가 구체적인가(구호성 아님) | LLM 의미 판단 |
| `measurability` | 개선 효과를 검증할 수 있는가 | LLM 의미 판단 |
| `example_ids_valid` | 근거 id가 실제 입력에 존재하는가 | **결정적 코드 검증**(LLM을 신뢰하지 않음) |

필수 항목(summary/top_issues) 누락 시에는 LLM을 부르지도 않고 즉시 FAIL — 품질 미달 산출물에 불필요한 LLM 비용을 쓰지 않는 사전 게이트입니다.

## 6. 과정에서 점검한 기술적 사항

- **모듈 무결성**: 전체 pytest 컬렉션(401개, 5차 개정 기준) 성공으로 문법적 완전성 확인.
- **예외 처리**: 빈 VOC 입력, Jira 조회 실패(502), 잘못된 엑셀 경로(400), LLM 미설정(400), 업로드 용량 초과(413), 지원하지 않는 확장자(400), 스키마 위반(재시도 후 502) — 모두 전용 테스트로 확인.
- **Provider 분기 및 오염 방지**: OpenAI/Anthropic/Custom/None 4가지 분기 + 독립 Judge 전환 시 `llm_model`/`llm_key_value` 오염 방지(16개 테스트).
- **테스트 격리**: 전체 pytest 실행이 실제 운영 파일(설정/실행이력/실사용자 데이터셋)을 건드리지 않는지 9개 테스트로 확인(2차 리뷰에서 발견된 P0, 상세는 결함보고서).
- **게시판 권한 체계**: 삭제=관리자 전용, 수정/노출비노출=작성자 또는 관리자, 댓글 열람 권한 우회 차단(11개 테스트).
- **업로드 보안**: 5MB 상한, `.xlsx`만 허용, 경로 조작 방지(파일명 sanitize), 실패 시 파일 삭제.
- **결과 무결성**: 분석 ID 마이크로초+UUID 충돌 방지, `os.replace()` 원자적 저장, 관리자 삭제 기능.
- **프롬프트 인젝션 방어**: 데이터-지시 구분자 + 신뢰 경계 명시(완전한 방어를 보증하지는 않으나 표준 완화 조치를 적용).
- **E2E 통합 흐름**: HTTP 레벨(`TestClient`) + 실제 브라우저(Playwright, 게시판 CRUD/다중삭제/모달/VOC분석/취소버튼) + 실제 LLM 3개 시나리오, 4개 레이어로 검증.

## 7. 성공적인 품질평가라고 판단하는 근거

**근거 1. 요구사항-테스트 상호 추적성** — [`VOC_분석_파이프라인_결함보고서.md`](VOC_분석_파이프라인_결함보고서.md)의 모든 결함/기능에 전용 회귀 테스트가 대응하며 전부 통과.

**근거 2. 계층형 테스트 아키텍처** — 함수 단위(`qa_agent/voc_analysis.py` 55개) → HTTP API(`board_api` 11개 + `voc_analysis_api` 36개) → provider 분기(9개) → Jira 클라이언트(7개) → 테스트 격리(9개) → 실제 브라우저(Playwright) → 실제 LLM 6개 시나리오(1차 3+2차 3), 7개 레이어.

**근거 3. 네거티브 경로 병행 통과** — 정상 동작뿐 아니라 LLM 실패, 필수 항목 누락, 스키마 위반, 업로드 남용, 권한 우회 시도, **그리고 실제 환경에서 발생한 진짜 API 오류(모델 혼용, temperature 거부)**까지 전부 확인.

**근거 4. 생성-평가 행위 분리 + 실증** — "생성 provider ≠ 검증 provider"가 실제 3개 시나리오 모두에서 `cross_model: true`로 확인되었고, 실제 PASS/FAIL 판정과 그 근거까지 확보.

**근거 5. 영구 보존되는 품질 감사 데이터(삭제 정책 포함) + TXT·XML·HTML 3종 증적 + SHA-256 manifest** — 모든 VOC 분석 실행 결과는 `reports/voc_analysis/voc_{timestamp}_{uuid}.json`으로 저장되어 "지난 분석 이력"에서 재조회 가능하며, **관리자가 명시적으로 삭제하기 전까지는 자동 만료되지 않습니다.** `scripts/run_quality_audit.py`가 한 번의 실행으로 **사람이 읽는 로그(TXT), CI 연계용 JUnit(XML), 브라우저용 시각적 리포트(HTML)** 3종과, 세 파일의 SHA-256 해시·생성 시각·git SHA·JUnit tests/TXT passed/`--collect-only` 3중 카운트 일치 여부를 담은 manifest JSON을 동시에 산출합니다. 2차 개정 시점에 실제로 재실행해 358개 테스트 전체에 대한 4개 파일이 정상 생성되고 카운트가 전부 일치함을 확인했습니다(`reports/exports/audit_manifest_20260715_155613.json`, 저장소에는 커밋되지 않는 런타임 산출물). 4차 개정 시점에 다시 재실행해 383개로, 5차 개정 시점에 또 재실행해 **401개**로 재확인했습니다(`reports/exports/audit_manifest_20260716_120535.json`). 최신 총계는 `docs/테스트_결과.md`와 위 품질 대시보드 API가 실시간으로 반영합니다.

**근거 6. 완전 자동화된 재현** — `pytest -q` 한 줄로 401개 테스트(5차 개정 기준)가 매번 동일하게 재현됨을 연속 2회 실행 + 실제 파일 SHA-256/mtime 불변 검증으로 확인(테스트 자체가 실제 운영 데이터를 건드리지 않는다는 것까지 포함해 재현성을 검증).

**근거 7. E2E + 독립 Judge 통합 테스트, 그리고 실제 API 통합까지 합격** — 모킹 기반 통합 테스트뿐 아니라 실제 OpenAI+Anthropic API를 사용한 3개 시나리오까지 전부 성공적으로 완주(PASS 1건, FAIL 2건 — FAIL도 "정상적으로 판정이 내려졌다"는 의미에서 성공).

## 8. 이번 품질평가를 통해 실질적으로 얻은 성과

- ✔ **VOC의 구조화된 품질 데이터화**: 자연어 불만을 소스/빈도/심각도/개선안/근거 id까지 연결된 JSON으로 자동 변환·영구 저장(삭제 정책 포함).
- ✔ **자연어 지시로 관점을 좁힌 분석**: "~중심으로", "최근 N건만" 요청을 `focus_instruction`/`item_limit`로 반영, 게시판 포함 여부(`use_board`)까지 독립 제어(2장 실증).
- ✔ **자기평가 편향을 실제로 억제하는 구조**: provider 교차 선택이 3건 시나리오 모두 `cross_model: true`로 동작했고, **의미 수준의 오류(ID는 실재하지만 내용이 다른 주제)까지 실제로 잡아냈습니다.**
- ✔ **2차 검증 실패가 1차 결과를 파괴하지 않는 회복력**: 설계 의도가 실제 장애(모델 혼용 발견 이전)에서 검증됐고, 수정 후에는 실제 성공까지 확인.
- ✔ **관리자 전용 삭제/이력 관리로 VOC 증적 보호**: 게시글·댓글·분석이력 모두 삭제는 관리자만, 대량 삭제·이력 삭제 기능까지 갖춤.
- ✔ **결함을 스스로 찾아 고치는 품질 프로세스 실증**: 독립 리뷰로 발견된 P0 7건 + P1 6건을 전부 실제로 수정·재검증한 것 자체가, "검증되지 않은 것을 통과로 표시하지 않는다"는 이 보고서의 원칙이 코드에도 일관되게 적용됐음을 보여줍니다.

## 9. 성공 판정의 합리적 범위와 한계

### ✅ 현재 품질 검증이 안전하게 입증된 범위

- 게시판(일반/FAQ/VOC) CRUD·댓글·권한 체계(다중삭제, 열람권한우회 방지 포함) 27개 테스트 전면 통과
- VOC 분석 생성 파이프라인, `use_board`/`focus_instruction`/`item_limit` 옵션, LLM 출력 스키마 검증
- 독립 Judge 로직(4개 의미 기준 + 1개 결정적 기준) 및 provider 교차 선택(오염 방지 포함)
- **독립 Judge의 실제 크로스모델 PASS/FAIL이 실제 API로 확인됨**(1차 보고서의 한계였던 부분 — 해소)
- 업로드 보안(용량/확장자/경로조작 방지), 결과 ID 충돌 방지, 프롬프트 인젝션 완화 조치(VOC 원문 + 6차 개정에서 확장한 `focus_instruction` 신뢰 경계 분리 포함)
- 2차 검증 실패 시 우아한 성능저하(실제 장애로 실증) + Judge 오류 메시지 정제(`logger.exception`으로 서버 로그에만, 사용자에게는 정제된 메시지)
- **전체 pytest 실행이 실제 운영 데이터를 건드리지 않음**(2차 리뷰 P0-1, 회귀 테스트 9건 + 연속 2회 실행 해시 비교로 실증)
- **quality_gate 판정이 현재 코드로 실제 재현됨**(서버 재시작 후 3개 시나리오 재실행, 1건 APPROVED 실증)

### ⚠️ 추가 검증이 필요한 한계 (정직하게 남기는 범위)

- **테스트 스위트가 일부 실제 문서 파일에 영향을 줌**: `docs/테스트_결과.md`는 `conftest.py::pytest_terminal_summary`가 **모든 pytest 실행마다 항상 최신 결과로 재생성하도록 설계된 프로젝트 전체의 의도된 정책**입니다(이 문서 자체에 "자동 재생성" 안내가 명시돼 있음). VOC 기능이 아니라 프로젝트 전체 테스트 인프라의 사전 결정이라, 이번 리뷰 범위에서 임의로 되돌리지 않았습니다 — 변경하려면 별도의 프로젝트 차원 결정이 필요합니다. 반대로 `.env`의 실제 API 키를 pytest가 사용하지 않는 것(`_no_real_secrets_in_tests` autouse 픽스처)과, 자동화된 pytest 스위트에 라이브 LLM 호출이 전혀 없는 것(모두 모킹)은 이미 충족되어 있음을 확인했습니다.

- **Interpreter**: `classify_voc_items()`가 Summarizer 이전에 각 항목을 `complaint`/`praise`/`inquiry`/`risk` 4라벨로 먼저 분류하는 별도 LLM 호출을 추가했습니다. 독립 Judge와 같은 원칙(실패해도 SKIPPED/ERROR로만 표시하고 본 파이프라인을 막지 않음)을 그대로 따릅니다. 실제 OpenAI 호출로 배송지연 2건/칭찬 1건/문의 1건/위험표현 1건이 섞인 입력을 넣었을 때 top_issues에는 배송지연 2건만 정확히 집계됨을 확인했습니다.
- **04~06 자가 비평-교정 + 08 내부 재점검**: 하나의 메커니즘(`_self_check_and_refine`)으로 함께 구현했습니다. 생성에 쓴 바로 그 모델이 자기 결과를 재점검(08)하고, `FAIL`이면 그 피드백을 반영해 **딱 1회만** 재작성(04~06) — 무한 루프·비용 폭주를 막기 위한 명시적 상한입니다. 재작성 결과도 기존 스키마·근거ID 검증을 동일하게 통과해야 채택되고, 실패하면 원본 결과를 그대로 보존합니다(`REFINE_FAILED`로 정직 표시 — 부가 단계의 실패가 이미 성공한 생성 결과를 잃게 만들지 않는다는 원칙). 이 값싼 자기 재점검은 **독립 Judge(다른 provider)와 목적이 다른 별개 방어선**이며, 자기평가 편향 방지라는 원래 목적은 여전히 독립 Judge가 전담합니다.
- **검증**: 새 스키마 검증 함수·재시도 경로·FAIL→재작성 성공/실패 두 경로 모두 결정론적 fake 클라이언트로 정확히 재현하는 회귀 테스트를 추가하고(실제 LLM은 응답이 매번 달라 특정 실패 경로를 안정적으로 강제할 수 없음), 별도로 실제 OpenAI+Anthropic 호출로 종단 검증했습니다. 신규 테스트 18건을 포함해 전체 스위트 383개가 통과했습니다(`audit_manifest_20260716_111244.json`, 5차 개정에서 추가 18건이 더해져 401개로 재확인 — `audit_manifest_20260716_120535.json`).
- **부수적으로 발견·수정한 UI 결함**: 같은 세션에서 "게시판 등록 시간이 이상하다"는 신고를 받아 재현했습니다 — 서버는 UTC를 정확히 저장하지만 프론트(`formatTimestamp`)가 뷰어 PC의 OS 타임존에 의존해, KST가 아닌 환경에서는 정확히 9시간 적게 표시되는 결함이었습니다. `Intl.DateTimeFormat`으로 뷰어 설정과 무관하게 KST로 고정 변환하도록 수정했습니다.
- **VOC 분석이력 조회/삭제 정책 변경**(신규 요청 반영): 조회(`GET /history`, `GET /{id}`)를 실행자 격리에서 게시판/Jira 티켓과 동일한 전원 공개로 전환하고, 삭제(`DELETE /{id}`)는 "관리자 전용"에서 "관리자 또는 그 분석을 실행한 본인"으로 완화했습니다. 제3자는 여전히 남의 실행 결과를 지울 수 없음을 전용 테스트로 확인했습니다.

**남아 있는 한계(4차 개정 시점)**: Retriever+Summarizer는 여전히 1회 호출로 통합(9장 참고 — 판단 기준이 늘지 않는 구간이라는 근거), PII 마스킹 미구현, 부하 테스트 미실시는 3차 개정과 동일하게 남아 있었습니다.

**5차 개정(이번 개정) — 남은 한계 3건 중 3건 처리**: 4차 개정이 남긴 위 한계 중 "Retriever+Summarizer 통합 유지"를 제외한 나머지를 전부 처리했습니다.

- **PII 마스킹**: `mask_pii()`(정규식 기반)를 정규화 단계(`normalize_board_post`/`normalize_jira_issue`/`normalize_excel_row`)에 적용해, 이후 모든 LLM 프롬프트가 마스킹된 content만 받도록 했습니다. 전화번호는 `010-****-5678`처럼 앞3/뒤4자리만 남기고, 이메일은 로컬파트 첫 글자만, 주민등록번호는 생년월일 6자리만 남깁니다. 완전한 탐지를 보증하지 않는 표준적 완화 조치임을 명시합니다.
- **서버측 백그라운드 실행 + 폴링 + 취소**: QA 파이프라인의 `RUN_REGISTRY` 패턴을 그대로 재사용해 `POST /api/voc-analysis/run-async` 등 4개 엔드포인트를 추가했습니다(기존 동기 `/run`은 하위 호환 유지 — 기존 테스트/호출부에 영향 없음). 핵심은 `should_cancel` 콜백 — 각 단계(Interpreter→생성→내부재점검→독립Judge) 시작 직전에 취소 여부를 확인해, 이전엔 "취소를 눌러도 서버 쪽 LLM 호출이 계속 진행되던" 상태를 "다음 단계로는 넘어가지 않는" 수준까지 실질적으로 개선했습니다(이미 시작된 개별 LLM HTTP 요청 자체를 중간에 끊는 것은 여전히 기술적으로 불가능 — 과장하지 않고 명시).
- **부하 테스트**: `tests/k6/load_test.js`에 `LOAD_VOC_MODE=1` 모드를 추가해 실제로 로컬 인스턴스에 2 VU(각 1회, 총 2건의 실제 VOC 분석)를 동시 실행했습니다. 결과: 100% 성공, 완료까지 평균 31.1초(p95 32초), 앱 자체의 HTTP 처리 오버헤드는 p95 13.3ms로 무시할 수준 — 즉 지연시간의 병목은 애플리케이션이 아니라 LLM 호출 자체임을 확인했습니다. **정직한 한계**: 실행마다 실제 LLM 비용이 들어 수십~수백 VU 규모의 진짜 "대량 동시 처리" 검증까지는 이번에도 하지 않았습니다 — "부분 해소"입니다.

**최종적으로 남는 것**: Retriever+Summarizer 통합 유지(의도적 설계 결정, 1장 근거 참고), 대규모(수십~수백 VU) 부하 검증 미실시, 보험 업종 전문용어 정확도는 합성 데이터 검증만, `run_run_3~9.json` 복구 불가 — 이 4가지는 정직하게 남겨둡니다.
